**核心发现（实证，非推测）**：标准 JS 工具集命名为 `read_file`/`write_file`/`list_dir`/`shell`，而 Rust 内核出厂内置为 `fs.read_file`/`fs.write_file`/`fs.list_dir`/`shell.run`——**命名不匹配**。StepRunner 把工具路由到原生内核后，内核以「未知工具」返回 → 抛错 → 回退 JS（`stepRunner.ts:100-108`）。本基准插桩证明：**30 轮共 105 次工具调用，100% 回退 JS，0 次由 Rust 执行**。`--native` 对标准工具集的工具执行实质是「休眠态」。

**实测延迟**：JS 22.2ms/任务（≈45 任务/s）vs native 23.0ms/任务（≈43 任务/s）→ native 慢 3.7%（+815µs/任务），差额 = 每工具一次 ~44µs FFI 往返（每任务 ≈1965µs）+ 稍慢的原生 token 估算（#70 已证）。两模式正确性完全一致。

**结论与下一步**：FFI 投资（#65–#67 手写 N-API 插件 + OS 沙箱 + 审批/沙箱全链）已具备能力，但**因命名桥缺失，标准 agent 循环从未真正走原生执行**——Rust 内核的 OS 级沙箱 `shell.run`、原生 `fs.*` 收益被锁死。唯一已生效的下沉是 token 估算（且偏慢）。激活真实收益的可行下一步 **#72 工具名别名桥**：在 StepRunner 注入 `read_file→fs.read_file` / `write_file→fs.write_file` / `list_dir→fs.list_dir` / `shell→shell.run` 映射（而非改模型口述），使标准工具集真正下沉 Rust，兑现 in-process OS 沙箱 + 原生 fs。

**关键设计**：

- **复用主循环而非另写一套**：子代跑的是同一个 `Agent`，因此自动继承上下文压缩、工具结果外溢（Spill）、FFI 原生后端等全部既有能力，零重复实现。本轮只做「隔离视图装配」+「度量」。
- **三道约束缺一不可**：① 深度闸门（`depth >= maxDepth` 拒绝）；② 并发闸门（所有子代共享进程内模型/存储/FFI 资源，无闸门会被长任务拖垮）；③ 父子树（`childrenOf(parent)` 可追溯，否则子智能体是黑盒）。
- **防递归双保险**：子代工具视图**强制剔除 `subagent` 自身**（`ToolSubset` 过滤），即便深度闸门被误配也无法无限套娃。
- **子轨迹隔离**：一次子代运行可产生数十条事件，逐条灌进父事件流会淹没主会话；改为事件桥内部收集、随结果返回，既保留完整审计又保持主会话清爽。
- **循环依赖的解法**：`ConfigFactory.defaultTools` 要在 runtime 装配完成前注册 `subagent` 工具，而编排器又依赖工具端口——故投影出 `SubagentPorts` 最小端口集（`tools` 字段回填为正在构造的注册表，构造期循环引用在运行时解引用，无害）。

### 顺带修复

- `src/adapters/tool/registryToolPort.ts`：参数校验原用 `typeof` 判类型，而 `typeof []` 为 `'object'`——**任何 `array` 类型参数都会被误判拒绝**（`subagent` 的 `tools` 白名单参数正需要它）。新增 `matchesType`/`typeNameOf` 特判 `array` 与 `null`。
