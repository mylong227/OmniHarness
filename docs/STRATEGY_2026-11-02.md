> **性质**：战略决策文档（带日期快照）。不改动 `PROJECT_BOARD.md` 的任何进度状态——看板仍是唯一事实源。

> **必须能在中国大陆离线/私有化部署**；**不做销售/客服类对外工作**；成功定义同时想要「自用顺手 + 开源有真实用户 + 有人付钱」。

## 0. 一页结论（先看这一段）

1. **你的瓶颈不是能力，是「可维护性 × 分发」。** 7 周写了 21.2 万行、4400+ 测试、0 star、0 issue、npm 未发布。
   这个组合说明：**工程产能已经过剩，而外部信号为零**。继续加能力，边际收益 ≈ 0，边际维护成本是复利。
2. **<10 小时/周 撑不住「平台 + 企业 open-core」的交付节奏。** 日常维护的均值尚可（约 9–18 h/月，见 §1.3），
   但**一次依赖断裂就是 10–25 小时**——均值能撑、方差撑不住；而 open-core 还要叠加持续的销售、合规与支持，
   这三项没有一项能在 10h/周里成立。**同时要「开源有真实用户」和「有人付钱」且不销售——这三件事在 10h/周下只能选一个半。**
3. **外部格局已经关闭了「再做一个通用 harness」的窗口。** 2026-08-20 OpenAI 把 Codex harness 以 Apache-2.0 开源
   （含 SDK 与 `app-server`）；Gemini CLI 已停服转 Antigravity；OpenCode 22 万 star 且做模型分销；
   国内 Kimi/MiMo/Qwen/Grok 全部自带 harness。**执行循环已经商品化，免费且更强。**
4. **唯一还对第三方开放的生态位是「治理层」：审计、回放、预算、长任务可靠性。** 这与你的资产高度重合
   （事件溯源、哈希链审计、审批六档、checkpoint、指标、ACP/MCP）——**但只在你把它做成「一个 5 分钟能验证的尖点」时才有意义。**
5. **推荐路线 R4：收缩 + 单点外化。** 把项目从「通用 harness 平台」收缩成「可审计执行内核」，
   并把其中唯一具备跨工具价值的东西做成独立开源工具：**Agent 审计出证（audit / attestation）**——
   能读 Claude Code / Codex / ACP / 自家会话，产出**可独立复核的哈希链审计报告**（谁批准、改了什么、花了多少、为什么失败）
   与可回放轨迹。注意「回放/抓包」已有人做（`acp-devtools`，MIT，周下载 4），**但它做的是协议调试，不是出证**——
   企业要的是能交给内审/法务的那张纸。它**不与任何 harness 竞争**（反而互补），**不需要销售**（npm + 一篇文章），
   **维护面小**（解析 + 渲染），且天然是企业私有化需求的漏斗（inbound）。
6. **预言（详见 §5）**：维持现状 12 个月，**55% 概率**项目进入「0 用户 + 维护腐烂」状态；
   执行 R4 且完成 90 天判据，**30% 概率** 12 个月内到 300+ star、**15% 概率**拿到第一笔 inbound 付费。
   两个概率都不高——但在你的约束下，这是**唯一期望值为正**的选项。
7. **如果 90 天后外部信号仍为 0**：诚实地转 R5（纯自用 + 归档），把 README 改成「个人项目，不承诺支持」。
   这不是失败，是把「沉没成本」换成「可持续的个人工具」。

## 3. 诊断：五个不舒服但必须承认的事实

### F1 执行循环已经免费，而你过半的代码在重复它

`adapters` 47,799 行 + `server` 12,380 + `cli` 12,555 + `context` 12,418 + `core` 9,359 ≈ **9.5 万行**在做
「循环 / 接入 / 上下文 / 服务」——这些正是 Codex harness 免费开源的那部分。
**你真正稀缺的部分是 `security` + 审计链 + checkpoint + 回放 + 审批**，它们只有约 1–2 万行。

### F2 内部指标繁荣，外部指标空白

4423 个单测、85.7% 覆盖率、函数体 ≤80、文件 ≤810 行、变异测试、仪器自证——**全部是内部一致性指标**。
但对外部世界唯一重要的问题是：**在一台陌生机器上、用真实模型、跑一个真实仓库的任务，成功率是多少？**
看板里 `eval:long` 最新记录是 **`--self-check` 40 passed**（自检，不是真跑）；`smoke:model`/`smoke:ui`
因成本「刻意不跑」。**推断**：**你没有任何一条对外可引用的任务级成功率。** 这不是你的错，但这是所有对外叙事的地基。

### F3 分发缺席，而且被「工程惯性」掩盖

90 个 npm scripts、45 份文档、7,665 行看板——这些是**做给已经在这个仓库里的人看的**。
而新用户的第一步是：clone → npm install（12 个依赖）→ 构建 164K 行 → 拿 token → **还要自己配 API key**。
**从「看到」到「感到有用」的路径太长，且没有任何一步能在 60 秒内给出「哇」。**

### F4 你的三个硬约束互相打架

- 要「有人付钱」⇒ 需要企业客户 ⇒ 需要销售/交付/合规认证；
- 「不做销售/客服」⇒ 只能 inbound ⇒ 需要先有可见度 ⇒ 需要分发；
- 「<10h/周」⇒ 分发生效需要持续输出（文章、issue 回复、demo）⇒ 与维护预算冲突。

**结论**：三者不可能同时满足。**必须放弃一个半。** 我的建议是：**放弃「短期收入」，把「开源真实用户」压到「一个尖点 + 一篇文章」的最小形态**，
自用价值作为兜底。

### F5 规模本身已经是最大的竞品

一个 <10h/周 的维护者，面对 203K 行 + 723 测试文件，最理性的行为是**不再改动它**——
一旦不再改动，它就在 6–12 个月内腐烂（依赖漂移、Node 版本、Chrome 升级）。**「大而全」在单人项目里不是资产，是负债。**

## 5. 预言：三种 2027-11 的世界

> 预测纪律：每条都写**触发条件**与**可观察的证伪点**。2027-02-01 与 2027-11-02 各复核一次。

### 世界 A：惯性继续（不改变当前节奏）——概率 **0.55**

- 2027-02：star ≤ 5；`npm start` 在干净环境至少失败一次（Node/依赖漂移）；全量回归红且 >7 天未修。
- 2027-11：代码 25–30 万行；star < 20；无外部 issue；你自己也改用别的工具干活；仓库进入「只读纪念品」状态。
- **证伪点**：如果 2027-02 时 star ≥ 30 或有 ≥3 个外部 issue，则本预测为假。

### 世界 B：R4 执行到位——概率 **0.25**

- 2027-02：审计出证 MVP 发布；一篇讲「agent 到底改了什么」的长文；npm 周下载 ≥ 20；star 30–80。
- 2027-11：star 300–800；≥1 个外部贡献者；≥1 次 inbound 企业咨询（付费与否不确定）。
- **期望值**：star ≥300 的概率 **0.30**，≥1000 的概率 **0.12**，第一笔 inbound 付费 **0.15**。
- **证伪点**：若 2027-11 star < 50，则本预测为假。

### 世界 C：市场窗口关闭——概率 **0.20**

- 2027 上半年，Codex `app-server` 或 Claude Code hooks 演化出「一等公民的 session 审计/回放」；
  或 `acp-devtools` 这类工具补上「出证」一层；或某家（Coder / LangSmith / Braintrust）把「agent 飞行记录仪」做成标准品。
- **对你的含义**：R4 的窗口只有 **6–12 个月**。若 90 天内拿不出可演示的 MVP，这条路线**应当主动放弃**，转 R5。
- 监测信号：`codex app-server` 的 changelog、Claude Code 的 hooks/transcript 文档、Coder Agents release notes。

### 三条更底层的判断（与路线无关）

1. **12–24 个月内，通用 harness 的独立生存概率 < 20%**；治理/审计层的生存概率 > 50%。
2. **star 与 LOC 的相关系数 ≈ 0**；与「一篇能被转发的文章 + 一个 5 分钟 demo」强相关。
3. **「诚实工程」是稀缺资产，但它只在被看见时才有价值**——你现在有 100 分的诚实、0 分的可见度。

## 6. 推荐路线 R4：收缩 + 单点外化

### 6.1 一句话战略

> **不再做「更好的 Claude Code」，改做「所有 agent 的审计出证器」——把 OmniHarness 从平台收缩为内核，
> 让唯一外化的工具成为分发入口，让 harness 成为它的后端。**
>
> 一句话对外文案：**「你的 agent 到底改了什么？——一条命令，一张可独立复核的审计报告。」**

### 6.2 为什么是「审计出证」（飞行记录仪这个比喻只能用来解释，不能用来定位）

| 判据           | 为什么它成立                                                                 |
| -------------- | ---------------------------------------------------------------------------- |
| 需求真实       | 企业要回答「谁在何时让 agent 改了什么、花了多少、为什么失败」；DORA/合规正在把这件事变成采购项 |
| 已有人验证     | `acp-devtools`（MIT，ACP 代理 + 抓包 + 回放 + diff + MCP，**npm 周下载仅 4**）证明这条路有人走、但没走通——**需求存在，注意力未到** |
| 差异点清晰     | 它做的是**协议调试**（JSON-RPC 帧）；企业要的是**出证**（哈希链 + 审批 + 变更 + 成本 + 可独立复核）。前者正在商品化，后者仍是空的——**这才是你该占的位** |
| 不与人竞争     | 它读别人的会话，是补集不是替代品——Claude Code/Codex 用户越多，它越有用       |
| 复用现有资产   | 事件溯源 + 哈希链审计 + 审批记录 + 回放 + 指标，全是你已经写好的              |
| 维护面小       | 解析器 + 报告渲染；**不接模型、不跑工具、不需要 API key**                     |
| 5 分钟见效     | `npx` 一条命令读一份 session 文件 → 一张可校验的报告，无需注册、无需配置      |
| 天然 inbound   | 要私有化部署审计中台的企业，会顺着这个工具找上门（这正是 R3 的正确形态）     |

### 6.3 产品边界（做什么 / 不做什么）

**做**（MVP，≤ 6 周净工时）：

1. `omniharness audit <file|dir>`：输入 4 种会话来源——自家 JSONL、ACP session、Claude Code transcript、Codex session；
2. 输出：单文件 HTML（离线可开）+ Markdown 摘要，含**时间线 / 工具调用 / 审批记录 / 文件变更 / 成本 / 失败点**；
3. **哈希链校验**：报告自带可重算载荷，收证方可独立复核（复用 `evolution lineage` 的口径）；
4. **诚实降级**：不认识的格式直接说「不支持」，**不猜、不补**（这是你的文化，也是最好的差异点）。

**不做**（明确排除，写进 README）：

- 不做新的 agent 循环、不做 provider 适配扩张（`adapters` 45K 行 → 砍到 3 个：OpenAI 兼容 / Anthropic / 本地）；
- 不做技能市场、不做多租户/计费（R3 的期权留给 inbound）；
- 不做自进化（增益未过两关，看板已判）；
- 不做桌面端新功能（冻结在「能启动」）。

### 6.4 90 天计划（按 <10h/周 排期，总预算 ≈ 120h）

**每周固定开销**：全量回归只跑 **1 次**（周日晚），其余用 `test:fast` 定向——把全量压到 15–25 min。

### 6.5 先花 7 小时证伪，再花 120 小时施工

这是本报告最省钱的一节：**在动工前，用 7 小时买一个「不建」的决定权**。

| 实验                                            | 成本 | 通过判据（否则不要开工）                             |
| ----------------------------------------------- | ---- | ---------------------------------------------------- |
| ① 手工做一份「审计报告」：拿你最近一次真实会话，用现有 `audit export` 凑出来 | 3h | 你自己看完能说出「这玩意儿我想每周看一次」            |
| ② 问 3 个真实用 Claude Code/Codex 的同行：你们怎么复盘 agent 改了什么 | 2h | 至少 1 人说「现在只能翻终端历史/靠记忆」= 痛点真实     |
| ③ 把 ① 的截图发一条帖子（200 字），不推销           | 2h | ≥5 条实质回复或 ≥3 次「在哪下载」= 需求存在           |

**三条全不通过** ⇒ 不要做 R4，直接进 R5（或把方法论写成文章，那是另一条成本更低的资产路线）。
**这一节的意义**：你已经用 8 周证明「能造」，现在要用 7 小时证明「有人要」——**后者才是稀缺信息**。

### 6.6 判据与 kill criteria（D90 = 2027-01-31）

**达标（继续 R4）**，满足任一：

- GitHub star ≥ 30 **或** ≥3 个外部 issue/讨论 **或** ≥1 个陌生人在 issue 里贴出自己的 session 文件；
- npm 周下载 ≥ 20（哪怕只是好奇）；
- 出现 1 个 inbound 的「我们想私有化部署审计」询问（不必成交）。

**不达标（转 R5）**：

- 上述全为 0 → 执行「优雅降级」：README 改为「个人项目，不承诺支持」；撤下 roadmap；
  停止新功能；只保留 `npm run regress` + 依赖安全更新；把审计出证器留在仓库里作为作品，不再运营。

**中间态（有信号但弱）**：把 R4 再续 90 天，但**预算砍半**（5h/周），只做 issue 响应与格式适配，不开新面。

## 7. 优雅降级路径（R5 的具体形态）

如果 D90 判据不达标，**不要硬撑**。降级不是失败，是把项目从「创业」切换到「资产」：

1. **README 重写**：一句话「个人 agent 实验平台，作者自用，不承诺支持」；
2. **冻结边界**：只维护 3 件事——`npm start` 能起、依赖安全更新、数据格式向后兼容；
3. **保留作品属性**：`docs/` 里的方法论（判据文化、变异测试、诚实清单）本身是有价值的写作素材，
   可以单独抽成 2–3 篇长文——**这是你真正的、不会被模型厂商品化的资产**；
4. **自用优先**：把审计出证器留给自己用（它对你调试 DSH/Claude Code 同样有用）；
5. **不再追 star**：star 是分发的结果，不是工程的奖赏。

## 8. 需要你拍板的三件事

1. **要不要接受「收入不是 3 个月目标」？** 在 <10h/周 + 不销售 + 全开源下，收入只能是 inbound 的副产品。
   如果不接受，就必须改一个约束（加时间 / 做销售 / 允许闭源企业版），否则目标不可达。
2. **要不要做「审计出证」这个尖点？** 它要求你从「造平台」转向「造一个工具」——
   情感上可能比技术上更难。替代品：把方法论写成系列长文（成本更低，但 star 增长更慢）。
3. **能不能接受「砍掉三到四成」？** 减法审计会删掉你写了很久的东西（45K 行 `adapters` 是大头）。
   如果做不到，R4 不成立，只能选 R5。
