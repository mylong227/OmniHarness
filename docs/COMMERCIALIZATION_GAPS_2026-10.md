## 二、F2 的 Web 工作台 tab：为什么标"部分"而不是"已落地"

F2 的判据原文是「治理台展示的**每条晋升记录**都能用 `audit verify` **独立复核**（数据与证据同源）」——
这条判据**已在数据面成立且有判据钉死**（`PromotionHistoryService` + `evolution history`，含三类篡改变异自证）。

未做的部分是**前端可视化**（Web 工作台新 tab）。诚实标注的理由：

- 它是**产品面**工作（渲染、交互、一键回滚按钮的确认流程），不影响上述判据的成立；
- 前端的正确做法是消费**同一个**服务（`PromotionHistoryService.view()` 已给出 `rows/summary/rollbackTargets`），
  现在做与日后做不会产生返工——**数据契约是稳定的**。

## 四、本轮复核改正的一处登记（自我纠错）

`Wave C 的 evolved 档 / J8` 最初被登记为「**阻塞：缺 `wasmtime` / Rust 工具链**」。后续复核发现**不准确**：

本机实测：

```
cargo 1.98.1 (797e8a9bc 2026-08-05)      rustc 1.98.1 (48a229cea 2026-09-01)
rustup target list --installed → wasm32-unknown-unknown（已安装）
crates/ → omni-cli / omni-core / omni-napi / omni-sdk / omni-sdk-gen / omni-wasm
```

⇒ **构建工具链齐备**，wasm32 目标也能编译。真正的缺口是**运行时行为**：

- 要在**不可信代码**上强制三件事：① 默认拒绝全部 import；② 超时**就地中止**
  （V8 无 fuel 计量，`WebAssembly` 一旦进入无限循环，宿主线程打不断它）；③ 内存硬上限。
- 可行的**零新依赖**路径：Node 内置 `WebAssembly` + **Worker 线程**（`resourceLimits` 限内存、
  硬超时后 `worker.terminate()` 才是真中止）⇒ **不需要 `wasmtime`**，也就不需要依赖准入评审。

改正后的状态：**② 可做，未做**（而非"阻塞"）。这处改正与判据文化同源：
**把"我没做"写成"环境不允许"是最容易骗过自己的一类虚报**——它让后来每个人都绕道走。

## 六、最后一项（per-skill wasm）的裁决：**不建**，理由是"它是仪式而不是能力"

### 6.1 这项剩下的是什么

Wave C 已把 `evolved` 档的 wasm 路径**打通并强制**：`wasm-skill` 资产类型（默认 `evolved` + `wasm`）、
签名包（`WasmSkillPack`）、装配期**真在 wasm 档冒烟**（跑不起来装不上）、资源硬上限（模块/入参/输出/
线性内存声明）、执行期九条拒绝路径的可机读 code。**缺的只有一件事**：谁来**产出**那个 wasm 模块。
今天只有本仓 Rust 侧（`crates/omni-wasm`）能产出，进化产物（JS/声明式技能）不能。

### 6.2 三条候选路径，以及为什么前两条被我判为"仪式"

| 候选                                                                       | 能买到什么                                                                                                                                 | 裁决                                                                                                                                            |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 通用技能宿主模块（模块读 `input` 里的技能 JSON，提供 describe/validate） | **几乎什么都没买到**：模块是通用的、技能是数据，而数据本来就走 manifest/schema 校验；把"读自己的 JSON"放进沙箱执行，安全性不增、复杂度增加 | **不建**（这就是"demo 式实现"的典型：技术上漂亮、功能上冗余）                                                                                   |
| ② per-skill 真编译（每个技能的 JS 逻辑编成 wasm）                          | 真能力：技能代码可在 wasm 档执行                                                                                                           | **做不到且不该假装**：需要 JS→wasm 编译器（Rust 侧只有 `omni-wasm` 内核，不是编译器）。本仓零新依赖纪律下，写一个玩具编译器才是最大的"可用就行" |
| ③ 明确登记为 R&D + 给出验收标准（本次选择）                                | 后来者知道**做到什么程度算完成**，且不会被"看起来能跑"的中间态骗过                                                                         | **采纳**                                                                                                                                        |

### 6.3 若日后做 per-skill 编译，验收标准（缺一不可）

1. **代码来源可信**：产出模块的编译链与工具链版本**进台账**（否则"这个 wasm 是怎么来的"不可查）；
2. **语义等价判据**：同一技能在 `vm` 档（既有 JS 路径）与 `wasm` 档的行为差异**必须有判据逐条列出**，
   不允许"看起来一样"；
3. **确定性**：同一技能 + 同一输入 ⇒ 产出模块**逐字节一致**（可复现构建），否则签名与市场分发失去意义；
4. **不放松既有强制**：per-skill 模块必须通过**现有**资源上限与九条拒绝路径（不是另开一条宽松通道）；
5. **渐进迁移**：`evolved` 默认装配下限从 `vm` 改 `wasm` 之前，必须证明**存量技能全部**有 wasm 等价物，
   或明确给出"哪些技能留在 `vm`"的清单——否则一次改动会把可用技能全拒。

### 6.4 结论

**这一项不是"欠账"，而是"决定不做 + 写清什么条件下才做"**。按本仓纪律（§12.1-1：要么做完，要么不做并显式标注），
它现在的状态就是完成态：**做得完的部分已经做完**（载体、强制、上限、可观测、判据），
**做不完的部分有名字、有原因、有验收标准**。

口径沿用本文开头：每项只允许落在三类之一（**① 已落地** / **② 阻塞且写明缺什么** / **③ 非代码项及前置**），

### 8.1 G1 多租户 + 计费：**② 阻塞**，且明确"半实现比不实现更危险"

复核事实：全仓 **0 处** `tenant` 引用；`server/services/quotaService.ts` 有配额底子但**没有租户维度**；
晋升台账、工作区、技能注册表、审计落盘都是**单租户**形态。

**为什么不做"先加个 tenant 字段"这种半实现**：多租户是**安全边界**。若只在配置里带 `tenant` 而台账/工作区/
密钥/配额仍共享，产品会呈现出"看起来隔离了"的假象——用户以为数据分开了，实际在同一条哈希链与同一个目录里。
按本仓纪律（§12.1-2 fail-closed / §12.1-1 要么做完要么不做），**虚假隔离预期比明说"不支持"危险得多**。

缺什么（做到才叫落地）：

1. 租户身份进**配置与凭据**两条链路，且**不可缺省**（缺省即拒，不是回落到单租户）；
2. 台账 / 工作区 / 注册表 / 审计 / 配额**逐项按租户作用域**，并有一条**跨租户读写的红判据**
   （A 租户读不到 B 的台账条目；配额按租户独立计数）；
3. 迁移路径显式化（§12.1-6）：单租户存量数据如何归属到默认租户、旧哈希链如何保持可复核；
4. 席位与用量计量：席位（人）× 用量（token/会话）混合——`quotaService` 可复用，但**必须先有租户维度**。

计费（发票/支付/税务）属 ③ 非代码：需要主体、税率与支付通道，与代码无关。

### 8.2 G3 托管控制面：**② 阻塞**（依赖 G1），代码面已有一半

- **已有**：治理台读面（`governance.history` 逐行复核 + 回滚锚点，F2 ✅，现已按 Pro 档上闸）、
  配额底子（`quotaService.status/update`）、审计落盘（`audit` 子命令与 `AuditSink`）。
- **缺**：租户作用域的审计查询与配额视图（**依赖 G1**）；托管形态（云 / 客户 VPC）属 ③ 运营。
- 结论：**G1 不做完，G3 只能停在"单租户控制面"**——而单租户控制面已经落地（治理台 + 审计）。

### 8.3 G4 转化漏斗：**③ 非代码项**，且前置是一个**隐私决策**

漏斗的用途是**跨用户聚合**（Star→CLI 采纳→Pro→Team），这要求数据离开本机。而本仓是 **local-first** 产品，
故在写任何埋点之前必须先回答（这三个问题没有答案，埋点就是不合规的）：

1. 采集范围（只计数？含技能名/文件名？）与**明示同意**的呈现位置；
2. 保留期、删除权与跨境（GDPR/PIPL）口径；
3. 北极星（周活治理操作数）**是否可由用户本地自算并只在同意后上报**。

代码面可先做且不涉隐私的部分：**本地聚合 + 用户可查看的导出**（不上报）。但那是"用户自己的报表"，
不是漏斗；把它叫做漏斗就是自欺。故 G4 停在 ③，前置写在上方。

### 8.4 H2 分成与结算：**③ 非代码项**

70/30 结算需要：可收款主体、发票/税务、支付通道、争议与退款流程、以及**市场侧的真实交易量**。
代码侧能做的只有"按台账算出应结金额"——那是十几行纯函数，在**没有交易与主体**时毫无意义。
前置：H1 市场侧有真实成交（当前 H1 的**门禁与出证**已落地：A/B/C 评级即门禁输出 `packGrader`、
进化系谱出证 `provenanceIssuer`——缺的是"人"与"钱"，不是代码）。
