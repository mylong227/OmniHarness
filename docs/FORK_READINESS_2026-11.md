## 0. 语义校准：开源 = 授予 fork 权，不是营销

按你的定义：**代码公开在 GitHub、任何人可拉取、可修改、可二次开发**。
这件事**已经成立**——仓库 public、Apache-2.0、无 CLA、无额外限制。

所以「准备开源」真正要准备的，不是发布会，而是**别人拉下来之后能不能改得动**。这两件事的判据完全不同：

| 目标           | 成功判据                     | 该做的事                       |
| -------------- | ---------------------------- | ------------------------------ |
| 对外发布/宣传  | star、下载量、讨论量         | 首屏、GIF、渠道、发布日        |
| **可二次开发** | **fork 数、下游项目、外部 PR、扩展点被使用** | **契约、扩展点、示例、可读性、构建可复现** |

本文件只服务第二行。**注意**：第二行比第一行便宜得多——它不需要运营、不需要渠道、不需要回应所有陌生人，
只需要**把接缝露出来并保证不随便破**。这与 10 h/周 是相容的。

## 1. 判断：这类项目的三种死法

二次开发者的失败，几乎总是这三种之一，而不是「功能不够」：

1. **能跑但改不动**——耦合。改 UI 要动内核，换模型要改十处 import。
2. **能读但接不上**——没有扩展点。想加一个工具，只能改核心代码、然后永远维护这个 fork。
3. **接上了但一升级就崩**——没有契约。作者一重构，下游全红，于是下游锁死版本、再也不 rebase。

**这三种死法的解药都不是"更多功能"，而是三种工程产物**：分层（kernel / contracts / apps）、
扩展点（五类）、契约（版本 + 弃用 + 格式兼容）。**这也是本文件全部内容的主轴。**

| 资产                     | 证据                                                                 | 对二开的意义                     |

| 架构文档                 | `docs/ARCHITECTURE_SPEC.md`（按现状重写）+ 19 份 ADR                  | 有读入口                         |
| 许可                     | Apache-2.0，无 CLA                                                    | fork 没有法律障碍                |

### 2.2 缺的（按「会不会挡住二开」排序）

| # | 缺口 | 实测 | 后果 |
| - | ---- | ---- | ---- |
| 1 | **没有「怎么改」的文档** | `src/` 下 **0 个** 模块 README | 1305 个文件，外人不知道从哪进 |
| 2 | **扩展点示例不齐** | 只有 plugin/tool 有；provider / workflow / UI **各 0 个可跑样例** | 想换模型/换 UI 的人卡在第一天 |
| 3 | **构建路径未跨平台验证** | 原生内核构建脚本为 **Windows-GNU 专用**（`ci.yml` 注释自述）；有 TS 回退 | macOS/Linux 的人会以为项目坏了 |
| 4 | **CI 红** | 累计 545 个 run，抽样最近 8 次全失败；`desktop` 为 `startup_failure` | fork 者第一眼看 badge，判定「这项目凉了」 |

| 6 | **贡献入口缺失** | 无根 `CONTRIBUTING.md`、无 CoC、无 issue/PR 模板 | 外部输入质量不可控，直接消耗你 10h/周 |
| 7 | **纪律门槛对外过重** | 90 个 npm scripts、10 条 fast 门禁、函数体 ≤80、文件 ≤810 | 只想改一行 UI 的人被 6 条门禁劝退 |
| 8 | **合同边界未公开** | `src/enterprise/` 与全仓同为 Apache-2.0，但文档没说清 | 下游担心「哪天变闭源」 |
| 9 | **第三方资产暗礁** | `NOTICE` 声明含 ComfyBench 衍生材料，需先读 `THIRD_PARTY_ASSETS.md` | fork 后重新分发可能踩上游条款 |
| 10 | **仓库噪音** | 21 个残留 `omni-sub-wt_*` 分支；`PROJECT_BOARD.md` 7,665 行 | 外人以为这是内部工作区，不是产品 |

## 3. 方向决策：Framework-first（内核 + 契约 + 参考实现）

这是本次要拍板的**唯一方向问题**：项目把自己定义成「应用」还是「框架」。

| 维度 | 作为应用（现状） | 作为框架（建议） |
| ---- | ---------------- | ---------------- |
| 产品 | CLI + Web 工作台 | **内核 + 契约**；CLI/Web/Desktop 降级为**参考实现** |
| 成功 | 用户量 | **fork 数、下游项目、外部 PR** |
| 你要维护的 | 全部体验 | **契约 + 一个参考实现**（下游自己维护他们的 UI） |
| 升级风险 | 每个下游都找你 | 契约不破，下游自己 rebase |
| 与 10h/周 | 不兼容（体验是无底洞） | **兼容**（契约变化频率远低于功能） |

**建议**：把项目明确定义为 **framework**，分三层，并且**用目录与文档把这条线画出来**：

```
kernel/       内核：主循环、上下文、工具、门禁、审计、存储   ← 你维护，稳定
contracts/    契约：ports、事件 schema、会话格式、配置 schema、SDK  ← 你维护，semver 承诺
apps/         参考实现：CLI、Web、Desktop                    ← 你维护一个能跑的就够，下游可整层替换
```

**五类扩展点**（二开 90% 的需求落在这五类）：

| 扩展点   | 现实入口                                   | 现状           | 目标产物                          |
| -------- | ------------------------------------------ | -------------- | --------------------------------- |
| Provider | `adapters/model/*` + registry              | 有实现无样例   | `examples/providers/minimal/`     |
| Tool     | `--tool` / `ToolPort`                      | 有实现无文档   | `examples/tools/minimal/`         |
| Plugin   | `omni.plugin.json`                         | **有 8 个示例** | 保持，补一份「权限白名单速查」     |
| Workflow | `workflow --file`                          | 有实现无样例   | workflows 下的 pr-review 样例（规划产物） |
| UI       | `web/`（Vite + React）+ RPC/SSE            | 无「换皮」说明 | `HOW_TO_FORK.md` 的 UI 章节       |

**明确不承诺**（写进 README，防期待错位）：

- 不为下游提供定制开发/支持（issue 每周 triage 一次，超范围直接关并说明）；
- 不做插件市场、不做多租户 SaaS、不做 IDE 插件；
- 不保证跨大版本的**自动**迁移，只保证**弃用标注 + 一个版本的过渡期**。

## 4. P0 阻塞项（不修完不发「二开邀请」）

按「不修别人就改不动」排序，每项带验收。

### P0-1 一份「15 分钟改得动」的入口文档（6 h）

根目录 `CONTRIBUTING.md`，只写四件事：**怎么构建 → 怎么跑最小测试 → 五类扩展点去哪改 → 提 PR 前的门禁清单**。
**关键**：明确区分「必须绿」与「建议绿」——外部贡献者只需 `npm run test:fast` + 相关单测；
内部那 10 条 fast 门禁由 CI 与维护者兜底，**不要**让外人先学会你的全部纪律。

**验收**：一个没读过代码的人，按文档 15 分钟内把 `--mock` 跑起来，并改掉一个模型名。

### P0-2 三平台构建实测（5 h）

- Linux（WSL 或容器）、macOS、Windows 各跑一次 `npm install && npm start -- --mock`；
- 原生内核明确写「**可选**，Windows-GNU 目前唯一可构建，其余平台自动回退 TS」；
- 把实测结果（OS + Node 版本 + 用时）贴进 `docs/STARTUP.md`。

**验收**：`docs/STARTUP.md` 里有三行实测记录，且没有「仅 Windows 可用」的隐藏前提。

### P0-3 CI 换骨（6 h）★

7 个 job + 3-OS 矩阵 ⇒ 改成 **`ci.yml`（gate + unit，Linux，≤12 min）+ `nightly.yml`（全矩阵/rust/wasm/e2e）**，
`desktop.yml` 改手动触发。理由不是省钱，是**第一个印象**：fork 者看 badge，不看代码。

**验收**：`main` badge 绿；PR 首跑 < 15 min。

### P0-4 五类扩展点样例（8 h）

每类一个 **≤ 50 行、可运行、带一条单测** 的样例，统一挂在 `examples/<类别>/minimal/`，并加一个 `npm run example:<名>`。

**验收**：`npm run example:provider` 等五条命令全部退出码 0；examples 总览页用一页表格列全。

### P0-5 `HOW_TO_FORK.md`（6 h，见 §6）

**验收**：按文档能把包名/品牌换掉、把 UI 换掉、把模型换成自己的，且三步各自有可复现命令。

### P0-6 版本口径统一（2 h）

`API_VERSION`（契约）/ `package.json`（包）/ `API_STABILITY.md`（文档）三处对齐，写清「两个版本号各自何时 bump」。

**验收**：`npm run api:check` 绿；三处数字与规则一致。

### P0-7 许可与商标边界（2 h）

- 明确 **全仓 Apache-2.0**（含 `src/enterprise/`），不存在隐藏闭源区；
- 加一段商标规则：fork 后**必须改名**，不得使用 OmniHarness 名称/图标做衍生品宣传；
- `THIRD_PARTY_ASSETS.md` 在 README 里被显式引用（ComfyBench 衍生材料）。

**验收**：路人读 README 能回答「我能商用吗 / 我能改名吗 / 有什么资产要单独授权」。

### P0-8 仓库门面清理（3 h）

删 21 个 `omni-sub-wt_*` 残留分支；description 去掉「(local project)」；topics ≥6；README 首屏改成
「**可嵌入、可替换、可审计**」而不是「一键启动」。

**验收**：`git branch -r` 只剩 `main`；README 首屏 40 行内出现「可二次开发」的明确入口。

## 5. 四周计划（40 h）

| 周 | 动作 | 预算 | 交付 |
| -- | ---- | ---- | ---- |
| W1 | P0-3 CI 换骨 + P0-8 门面清理 | 9 h | badge 绿；分支干净；description/topics 改完 |
| W2 | P0-1 CONTRIBUTING + P0-2 三平台实测 | 11 h | 15 分钟上手文档 + 三行实测记录 |
| W3 | P0-4 五类扩展点样例 | 10 h | 5 个 `npm run example:*` 全绿 |
| W4 | P0-5 HOW_TO_FORK + P0-6 版本口径 + P0-7 许可说明 | 10 h | fork 指南 + 三处版本一致 + 商标/资产段 |

**顺序理由**：先修「第一印象」（CI/门面），再修「能不能上手」（贡献/构建），最后才是「怎么改」（样例/fork 指南）。
反过来的话，你会在没人能跑起来的情况下写一堆扩展文档。

## 6. `HOW_TO_FORK.md` 大纲（这份文件是二开的核心交付物）

市面上开源项目几乎都有 README，极少有「怎么把项目改成你自己的」——**这正是差异化**。

```md
# 把你的产品建在 OmniHarness 上

## 0. 先决定你要哪一种
A. 只用内核，UI 自己写        → 走 §2
B. 保留 CLI/Web，换模型/加工具 → 走 §1
C. 整仓 fork，改名做成自己的产品 → 走 §3

## 1. 最小改动：换模型 / 加工具 / 加插件
- 换模型：adapters/model 的注册点在哪（一个文件），最小 provider 示例
- 加工具：--tool 协议（definition/handler/权限声明），示例 20 行
- 加插件：omni.plugin.json 字段表 + 权限白名单速查 + 8 个官方示例索引

## 2. 只取内核：把 OmniHarness 当库
- import { Agent } from 'omniharness'（@public 面）
- 事件流：订阅哪些事件、哪些是契约（事件 schema 版本号）
- 存储：接自己的 session 存储（StoragePort）
- 一个 30 行的 headless 例子

## 3. 整仓 fork：改名换皮清单
- 必须改：package.json name/bin、图标题、logo、appId、userData 目录、OMNI_* 环境变量前缀
- 必须留：LICENSE、NOTICE、THIRD_PARTY_ASSETS 引用
- 建议关：遥测/更新检查（默认关，确认一次）
- 建议删：你不需要的模块（给出「删了会不会崩」的判据：无生产调用方 + 无公开导出）

## 4. 契约与升级
- 哪些 API 稳定（@public）/ 实验（@beta）
- 版本号怎么读（包版本 vs 契约版本）
- 弃用周期：标注后保留一个 minor
- 你 fork 之后怎么 rebase：建议只跟 `main` 的 tag，不跟每日提交
```

**写作纪律**：每一节都要有**可复现命令**，没有命令的段落不进文档（沿你的既有判据文化）。

## 7. 指标与退出条件

| 指标 | 为什么看它 | D30 目标 | D90 目标 |
| ---- | ---------- | -------- | -------- |
| fork 数 | 二开意图的最直接信号 | ≥5 | ≥30 |
| 下游项目（issue 里提到「我用它做了 X」） | 真实价值证据 | ≥1 | ≥3 |
| 外部 PR | 代码级参与 | ≥1 | ≥5 |
| 扩展点使用（issue 里的 plugin/provider/tool） | 接缝是否真的可用 | ≥2 | ≥10 |
| star | 只是噪音，作参考 | — | — |

**退出条件**：D90 时 fork <5 且外部 PR = 0 ⇒ 说明「可二开」这个卖点也没人接。
此时**不要再改代码**，转 R5：把方法论与模块地图写成文章（成本更低、留存更久），项目进入低维护模式。

## 9. 风险

| 风险 | 说明 | 对策 |
| ---- | ---- | ---- |
| 「改不动」比「没人用」更常见 | 203K 行、AI 生成、内部纪律重 | P0-4/P0-5 是解药；模块地图与五类样例优先于任何新功能 |
| 下游 fork 后不回馈 | 二开的常态 | 接受它；只要契约被用，就是影响力。别用「必须 PR 回来」做门槛 |
| 契约被你自己破坏 | 10h/周 下最容易发生 | 把 `api:check` 挂 CI 红线；每次 `@public` 变更必须写 changeset |
| 支持请求淹没你 | 一旦有人用，就会有人问 | README 明写 best-effort；issue 模板三问；超范围直接关 |
| 法律暗礁 | NOTICE 里的第三方资产 | P0-7 写清；README 显式链接 `THIRD_PARTY_ASSETS.md` |
| 方向再次漂移 | 这是本项目的最大历史风险 | 每个季度用本文件 §3 的三层图对一次：新代码落在哪一层？落不进去就是没想清楚 |

## 10. 一句话

**开源给的是「改的权利」，二开要的是「改得动的结构」。**
你已经有权利（Apache-2.0），现在缺的是结构——**把 kernel / contracts / apps 画出来，把五类扩展点做成能跑的样例，
再写一份别人照着就能改的 fork 指南**。这三件事做完，「可二次开发」才从一句声明变成一个事实。
