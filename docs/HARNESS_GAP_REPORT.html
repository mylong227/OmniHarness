先说结论。差距的本质不是「功能点少」，而是三个量级的工程投入差：OmniHarness 1.7 万行 vs dsh 约 40 万行 vs Codex 约 150 万行。 但 OmniHarness 在架构纯度（六边形端口-适配器、零运行时依赖、Rust 内核免工具链 FFI）上是三方里最干净的，且已把两个上游**最高价值的通用能力**（Spill 外溢、双 BM25 检索、沙箱升级审批、配置分层）补齐。 真正的差距集中在四类：① OS 级沙箱与网络隔离（几乎全缺）、② 长期记忆与会话重放（几乎全缺）、③ 人机交互面（无 TUI、无前端）、④ 生态与工程成熟度（无 LSP/git/OTel/预算闸门/回放测试）。
✅ 已具备且较完整 ⚠️ 有但残缺 / 简化 / 占位 ❌ 缺失 P0 致命缺口（影响可用性/安全性） P1 高价值（明确提升能力上限） P2 中等（补齐体验） P3 低（生态/锦上添花） 领先 OmniHarness 反过来强于两者

二、差距分级与补法建议

P0 致命缺口（5 项）—— 影响可用性或安全底线

P0-1 · OS 级沙箱形同虚设：三个后端全是 UnsupportedSandbox 占位
现状
--sandbox landlock|seatbelt|bwrap 落到 unsupportedSandbox.ts，一律拒绝执行。真实可用的只有 passthrough（无隔离）/ policy / restricted（用户态黑名单）。
上游
Codex Linux 走 seccomp（过滤 socket/connect）+ bwrap（独立网络 ns、打包二进制带摘要校验、失败专用退出码 8）+ landlock 兜底；macOS 4 个 sbpl 模板，只从 /usr/bin/sandbox-exec 取二进制防 PATH 注入；Windows 上 WFP 内核网络过滤 + 受限令牌 + ACL 递归拒绝读 + 防 junction 逃逸。dsh 自写 C11 musl 静态 landlock-run（裸 syscall 444/445/446，ABI 从 MAX_ABI=5 向下协商，任何失败 exit 125 绝不 exec 未受限进程），Windows 用受限令牌 + capability-SID 写白名单。
补法
不用重写。本工程 Windows 主力：优先补 Windows 受限令牌后端（CreateRestrictedToken(DISABLE_MAX_PRIVILEGE|LUA_TOKEN|WRITE_RESTRICTED) + restricting SID 写白名单，与 dsh sandbox-windows-acl 同构），这一步不需要管理员权限、不需要驱动。Linux 侧接 landlock-run 或 bwrap 外部二进制即可（保持 PlatformSandbox 接口不动）。
代价
Windows 后端约 400–600 行（需 koffi 或 N-API 调 Win32——可复用 #65 已有的 N-API 免工具链方案，不破坏零依赖铁律）；Linux 后端约 200 行 + 外部二进制分发。
P0-2 · 零网络隔离
现状
三方里 dsh 也没有，但 dsh 把「只管文件」显式写进类型与文档（SandboxEnforcement: full|partial），是诚实建模；OmniHarness 的 SandboxPort 连这个诚实度都没表达。
上游
Codex 是唯一做到的：独立网络命名空间 + HTTP/SOCKS5 代理 + MITM（rama 栈终结 CONNECT 隧道后对内层 HTTPS 做策略，自签 CA）+ 凭据代持（沙箱内注入 dummy 环境变量，真值只在代理侧替换，凭证永不进入被沙箱进程的内存/磁盘）+ Windows 端 TCP 连接归属到进程。
补法
最小可行：先把 NetworkSandboxPolicy 加进 SandboxPort 类型（对齐 Codex protocol/permissions.rs），实现「域名白名单 + 默认拒绝」的代理层。完整 MITM 与凭据代持工程量大，建议列为后续。
代价
类型层 + 代理层约 800–1200 行；MITM 另计 3000+ 行。
P0-3 · 长期记忆完全缺失（Codex 已做成 ETL 流水线）
现状
memory_search 是会话历史检索（BM25），不是跨会话沉淀的记忆。会话一结束，知识就锁死在 jsonl 里，下次会话不会自动获得。
上游
Codex memories/write：Phase1 对每条 rollout 用低推理档 LLM 抽取（并发 8、SQLite 作业租约 3600s 防重复、rollout 截断到上下文窗口 70%、输入先 redact_secrets 脱敏）；Phase2 抢全局锁 → 给记忆根目录建 git 基线仓库 → git diff 算变更（含扩展资源被删的信号，用于清理陈旧记忆）→ spawn 整合 agent 改写 MEMORY.md → 校验产物。工作区用 symlink 隔离，且显式拒绝操作符号链接的记忆根（防 symlink 攻击）。另有扩展记忆源（每个源自带 instructions.md）+ 7 天保留清理。
补法
最小可行版：Phase1（rollout → 低档抽取 → raw_memories.md）+ Phase2 的 git diff 整合。可完全复用现有的 RetrievalPort 与 BM25 做召回，租约、扩展源后置。
代价
最小版约 600–900 行 + 一个 MemoryPort。
P0-4 · 无持久 PTY，跑不了任何交互式程序
现状
shell 是一次性子进程。ssh、python REPL、vim、交互式安装向导、需要 TTY 的 CLI——全部无法使用。这是 agent 能力的硬边界。
上游
dsh terminal seam + 6 个工具（open/send/read/signal/close/list），terminal_close 会 await 所属进程树消失（不留孤儿），针对 shell 的 SIGKILL 被拒并引导用 close。Codex unified_exec（exec_command/write_stdin）+ utils/pty 跨平台（Windows ConPTY），输出 head_tail 缓冲 1MB 上限，往运行中的 PTY 写 stdin 也要走审批。
补法
Node 侧可用 child_process.spawn + 管道模拟，但真 PTY Windows 需要 ConPTY（node-pty 是原生模块，会破坏零依赖铁律）。务实路线：先做「持久 shell 会话」（保持一个长驻 bash/pwsh 子进程 + prompt 探测），不追求真 TTY；真 ConPTY 走 N-API 内核（复用 #65 方案）。
代价
持久 shell 约 400 行；真 PTY 走 N-API 约 1000+ 行。
P0-5 · 无 TUI，交互面只有一次性 CLI 文本
现状
无 TUI（Codex 有 28.8 万行），Web 前端只有两个演示级 html。审批、diff 审阅、多会话切换、进度感知全部缺失。长时间任务里用户是「盲等」。
上游
Codex tui：diff_render、审批覆盖层、撤回 backtrack、外部编辑器、hooks 浏览器、记忆设置面板、命令/文件搜索弹出、模型选择、插件目录、协作模式、剪贴板、IDE 上下文、宠物彩蛋。dsh 走 Web 路线：43 个 UI 插件 17.5 万行，含 trajectory 事件账本 + 交互式时间总览（罕见的「执行审计」UI）、工具调用树、多会话树、审批 composer 接管。
补法
先补 terminal 侧最小面：diff 彩色渲染 + 审批单键确认 + 流式输出 + 工具调用进度行（约 800–1500 行，零依赖可做到，用 ANSI 转义）。全功能 TUI 不现实也不必要——dsh 也没做，它把预算投在 Web 上。
代价
最小面约 1000–1500 行；完整 TUI 不推荐。

P1 高价值缺口（10 项）—— 明确提升能力上限

P1-1 · run_code 用 new Function，无隔离、无超时、无输出预算
现状
同进程执行任意代码。一个死循环卡死整个 harness，一次 console.log 巨量输出灌爆上下文。唯一做对的是程序内 call() 走 ToolGate。
上游
dsh 每次运行开全新 Worker 线程：LogBuffer 共享字节预算 + 流式 sink + 截断，失败是字段不是 rejection（CodeRunFailure kinds: exception/timeout/abort/worker-exit/invalid-output/output-limit），materializeFromRealm 拒绝非 JSON 值。Codex V8 进程内沙箱（v8_enable_sandbox，可 --jitless 关 JIT 缩攻击面）+ JSON Schema → TypeScript 自动类型绑定注入全局 + gRPC 分离进程 + CellId 单元格模型。
补法
Node 原生就有 worker_threads——零依赖即可换成 Worker 线程实现，加超时（worker.terminate()）与输出预算。这是投入产出比最高的一项。JSON Schema → TS 类型提示也值得抄：把工具定义渲染成类型声明塞进 run_code 描述里，模型写代码立刻类型正确。
代价
Worker 化约 250–400 行；Schema→TS 渲染约 200 行。
P1-2 · 无跨 agent 通信：子 agent 是「一次性投递」，中途无法交互
现状
subagent 工具发起 → 等结果返回。父不能中途追问，子不能主动汇报，子与子之间完全不通。
上游
Codex InterAgentCommunication：author / recipient / other_recipients / content / encrypted_content / trigger_turn（决定是否唤醒对方 turn）；完成通知 watcher 订阅子状态到终态再格式化回父路径；通信遥测明文时只记 [plaintext]。dsh agent-team 持久化对等邮箱（experimental）。
补法
新增 AgentMailboxPort（或直接扩展 EventPort 加 scope 路由），子 agent 持有 mailbox 引用；send_message / interrupt_agent / wait_agent 三工具即可对齐 dsh 的 tool-subagent-control。
代价
约 400–600 行。
P1-3 · WorkerOrchestrator 是 for 循环串行，无 DAG、无并行、无屏障
现状
delegateAll 逐个 await。无法表达「A、B 并行，都完成后再跑 C」，也没有环检测。
上游
dsh 主干 workflow 是脚本式（vm 沙箱注入 agent/parallel/pipeline/phase，FIFO 并发槽、AGENT_CAP、ITEM_CAP，但明确无跨 stage 屏障）；真 DAG 在 experimental/agent-team 的 task-board（blockedBy 依赖数组 + dependencies() 环检测 + ready 判定 = 所有 blocker 都 completed），默认不启用。Codex 不做 DAG，靠 code-mode 用代码编排替代。
补法
两条路：① 抄 dsh task-board 的最小 DAG（依赖数组 + 拓扑排序 + 环检测，约 300 行）；② 不做 DAG，改用 P1-1 强化后的 run_code 用代码编排（Codex 路线，更省）。建议走 ②——与已有 run_code 复用，成本低得多。
代价
路线 ① 约 300–500 行；路线 ② 约 0（依赖 P1-1）。
P1-4 · 无目标驱动长循环（goal / 自动续轮 / ralph）
现状
有 plan 与 todo，但都是被动的：模型自己决定做不做下一步，没有外部驱动器。
上游
dsh 双机制互补：goal = 持久目标 + 同会话自动续轮（GoalRef CAS 乐观锁、竞态栅栏 sameQueued/restoreOtherClaimed、静默期 agent.followup()、maxGoalRounds 闸门）；ralph = 固定脚本 + 每轮全新子 agent + 16KB 有界 handoff，最多 256 轮，模型只提供数据不能改循环/schema。Codex ext/goal + collaboration-mode-templates。
补法
新增 GoalPort + 一个 round driver（在 TurnRunner 静默期检查 goal.phase==='active' 且 armed 且未达上限 → 注入 followup）。竞态栅栏是这类功能最容易出错的地方，务必照抄 dsh 的 sameQueued + agent 局部串行驱动。
代价
约 500–800 行。
P1-5 · 无 LSP 集成
现状
完全无。模型只能靠 grep + 读文件理解代码结构。
上游
只有 dsh 有（lsp-stdio）：按需 spawn 外部语言服务器、按 canonical workspace 池化单实例、查询串行化、transport 失败换实例重试、$/cancelRequest、优雅 shutdown（SIGTERM→grace→SIGKILL）、workspace/applyEdit 一律拒绝。限制：只有 4 个只读操作（definition/references/implementation/hover），无 rename/format/diagnostics/symbols，且不随附任何语言服务器，二进制不存在则该 provider 静默不注册。
补法
照抄 dsh 的 stdio 桥接形态，做成 LspPort + 适配器。工作量主要在 LSP 协议编解码（Content-Length 分帧 + JSON-RPC）。
代价
约 600–900 行。
P1-6 · 无二级模型审批（Guardian）
现状
guardianApproval 存在但形态偏「提示词级」；无独立审阅会话、无超时熔断、无只读工具投影。
上游
Codex core/src/guardian/：重建紧凑转录（message 10k / tool 10k / 单条 2k / action 16k / 最近 40 条）→ 交给专用只读子会话（只注入 4 个 history 只读工具、不加载任何扩展防扩展反向影响判定）→ 要求严格 JSON → 90s 超时/执行失败/畸形一律 fail-closed → 连续拒绝 3 次熔断（cyber 场景 1 次，滑动窗口 50 次内最多 10 次）→ 用户手动改判后注入 developer message 让 Guardian 学习偏好。
补法
本工程已有 SubagentOrchestrator，起一个只读子会话零成本——只需定义工具投影（只给 history 类只读工具）+ 超时 fail-closed + 熔断计数。这是所有 P1 里复用度最高的一项。
代价
约 350–500 行。
P1-7 · 无 token / 成本硬预算
现状
有 tokenEstimator 能算，但没有闸门：不设上限、不告警、不限流。goal/ralph 类长循环一开就是无底洞。
上游
dsh 的 token-meter 是重放感知的（MeasurementAnchor + ReplayState + planSurfaceTokens/commitSurfaceTokens，保证锚定表面与当前表面用同一套 route pricing 重定价）——测量做得极严谨，但同样没有硬限额。Codex 有 rate_limits + rollout_budget + backend-client 用量读取。
补法
在 TurnRunner 加一个 BudgetGuard：会话级 / turn 级 / 工具级三个 token 与金额上限，触顶即停并回报模型。这是三方都没做好的空白区，本工程有机会做成一个领先项。
代价
约 200–350 行。
P1-8 · 无无密钥回放测试体系
现状
48 个测试文件靠 mock 模型。改一次提示词/装配，mock 不会告诉你真实链路坏了。
上游
dsh 三件套：llm-replay（录制 JSONL 重建 model chunk，短路 llm/stream）+ llm-mock-server（可脚本化的 OpenAI 兼容 故障服务器）+ session-snapshot（会话日志快照核 + ACP 适配器 + 期望输出归一化 + fixture 不变量）。且强制要求产品可见插件必须有 REAL-composition 测试（真实 Loader 装配），不许单测 mock 冒充。
补法
录制一次真实 LLM 交互为 JSONL fixture，mockModel 增加 replay 模式按序回放。配合已有的 333 用例，回归保护能力提升一个量级。
代价
约 300–500 行。
P1-9 · 会话无 trace 归约，无法离线重放分析
现状
eventLog 有事件流，但没分层、没归约模型、没缓存。想分析一次会话为什么失败，只能肉眼翻 jsonl。
上游
Codex rollout-trace：raw → reduced 两级。trace.jsonl 追加写原始事件（RawEventSeq 单调序号，大载荷外置为 RawPayloadRef），reducer/ 归约成语义模型并缓存到 REDUCED_STATE_FILE_NAME，覆盖推理尝试、MCP 调用、code cell、压缩检查点、工具分派、子 agent 回传（AgentResultTracePayload）全链路。这是 Codex 最被低估的能力。
补法
在 SessionRecorder 之上加一层 reducer：raw 事件不变，新增归约产物（对话树 / 工具调用树 / 检查点 / token 曲线）。可复用 output/jsonlWriter。
代价
约 400–700 行。
P1-10 · 压缩策略偏简，缺「阈值按比例 + 保留区 + 配对保护 + 溢出绕行」
现状
contextCompactor 有，但阈值是绝对值还是比例、是否保护 tool-call/result 配对、溢出路径如何处理——都未达上游精细度。
上游
dsh DEFAULT_THRESHOLD_RATIO=0.8 / RETAIN_RATIO=0.16，阈值与保留区都按 contextWindow 比例算，按 provider/model 可精确覆盖；retainTokens 必须 < thresholdTokens（否则抛 TargetPressureConfigError）；溢出绕过常规阈值；generation 守卫（压缩期间会话被改则本次作废）；toolPairingBalanced* 保证压缩边界不切断 tool-call/result 配对（切断后重放会崩）；另有纯确定性、不烧 token 的 head/middle/tail 裁剪器。Codex 另有配置 diff 增量注入（reference_context_item 基线），配置变更只注入差异。
补法
把阈值改成比例制 + 加配对保护 + 溢出路径。三项都不大，但直接决定长会话稳定性。
代价
约 250–400 行。

三、OmniHarness 的领先项（不要妄自菲薄）

领先项OmniHarness 做法两个上游的对照
零运行时依赖devDeps 仅 typescript + @types/node，运行时依赖为 0dsh 254 个 npm 包（含 @modelcontextprotocol/sdk、zod、react、koffi、@vscode/ripgrep…）；Codex Cargo.lock 1361 个包。这是架构纯度上的绝对领先——供应链攻击面、安装体积、版本地狱都小两个量级
免工具链的 N-API FFI从宿主 node.exe 用 GetProcAddress 动态解析 napi_* 符号 —— 免 MSVC、免 FFI 库、不破坏零依赖铁律dsh Windows 沙箱必须依赖 koffi（原生 FFI 库）；Codex 是 Rust 原生不需要 FFI。在 TS 侧这是独一份的解法，且正好规避本环境"无 MSVC / 无管理员权限"的死结
双 BM25 检索（工具 + 会话）自研 Okapi BM25，双语文法：ASCII≥2 + snake_case 拆子词 + CJK 一元/二元；tool_search 命中→下回合可见→可调用，闭环完整dsh 用 SQLite FTS5 + unicode61——对中文不友好（无 CJK 二元切分），且 Web 面默认把 FTS 关成 :memory: + openAt: never；Codex 未见专门会话检索。中文检索质量 OmniHarness 明显更好
MCP 双向client + server + gateway + toolMapper 全套dsh 只有 client，官方承认不能把 dsh 的工具暴露给外部；Codex 虽双向但依赖 rmcp 生态。OmniHarness 用零依赖做到了双向
Spill 外溢#75：钩子拿完整结果之后、写入模型上下文之前外溢；spill_read 必须豁免外溢（否则模型永远取不回全文）；FileSpill 用 ^[A-Za-z0-9_-]+$ 白名单防穿越。与 Compaction 形成「先剪后压」双层防护dsh 也有（head/tail 预览 + locator），但Codex 完全没有——Codex 侧要么粗暴截断要么全量灌入。OmniHarness 与 dsh 并列第一梯队
配置四层合并 + fail-closed用户级→项目级→profile→env 四层，每层严格校验，非法即抛 ConfigError 而非静默回退内置默认dsh 用 cordis.yml 补丁层（组合能力强但无严格校验层）；Codex 有 ConfigLayerStack 但更偏企业托管。「非法配置不静默降级」是本工程修过的一个真实缺陷，两个上游都未显式处理
子 agent 复用主循环子代跑同一个 Agent（只换 tools/events/maxSteps 的隔离 runtime 视图）→ 自动继承压缩、Spill、FFI，零重复实现dsh 进程内/进程外各写一套驱动；Codex 是 ThreadManager + AgentControl 独立控制平面。OmniHarness 用极少代码拿到了同等能力，这是"小体量打赢大体量"的样板
沙箱诚实度不支持的后端一律 UnsupportedSandbox fail-closed，绝不谎称隔离dsh 有 SandboxEnforcement: full|partial 显式标注（同样诚实）；Codex 平台后端是真的。这是"缺能力但不缺品格"——比假装隔离好
子轨迹隔离SubagentEventBridge 内部收集、随结果返回，不广播父事件流（否则数十条子事件淹没主会话）dsh 靠 scope 过滤；Codex 子 agent 完成才回传。等价，但本工程实现更轻

四、建议优先级路线

阶段目标内容判断依据
第一步
性价比		把已有的「半成品」做实① run_code 换 Worker 线程（P1-1）② 压缩改比例制 + 配对保护（P1-10）③ BudgetGuard（P1-7）④ 会话检索 fixture 回放测试（P1-8）四项合计约 1200–1800 行，全是复用现有端口，且 P1-7 有机会做成三方都没有的领先项
第二步
安全底线		把沙箱从"用户态黑名单"提升到"OS 级"① Windows 受限令牌后端（P0-1）② NetworkSandboxPolicy 域名白名单（P0-2）③ 命令规范化 + 审批→策略持久化（P1）Windows 后端可用 #65 已有的 N-API 方案调 Win32，不需要 koffi、不需要管理员权限，是本环境唯一可行路径
第三步
能力上限		把 agent 从"单轮执行"提升到"自主长循环"① Guardian 二级审批（P1-6，复用 SubagentOrchestrator）② GoalPort + 竞态栅栏（P1-4）③ 跨 agent 通信（P1-2）④ 长期记忆最小版（P0-3）四项互相咬合：没有 Guardian 就不敢开自主循环，没有 BudgetGuard 就不敢开长循环，没有记忆长循环就重复犯错
第四步
可用性		补交互面① terminal 最小面（diff 渲染 + 审批单键 + 流式 + 进度行，P0-5）② 持久 shell 会话（P0-4）③ Web 前端接到 server 上dsh 也没做 TUI（它把预算投 Web），说明 TUI 不是必选项；但 diff 渲染 + 审批交互是刚需，必须补
不建议
暂缓		——DAG 编排（改用 run_code 代码编排，Codex 路线）· MITM 凭证代持 · Agent 密码学身份 · 实时语音 · 连接器生态 · 完整 TUI要么依赖中心化后端、要么工程量与收益不成比例、要么有更省的替代路线
最后一句话总结。 OmniHarness 用 1.7 万行 做到了 dsh（40 万行）与 Codex（150 万行）约 55%–60% 的核心能力面，架构纯度与零依赖是三方最优； 但在沙箱真实性、长期记忆、交互面、工程基建四条线上是结构性缺失——这四项合计约占差距权重的 70%。 按上面的四步路线，前两步（约 3000–4000 行）就能把"能不能用"和"敢不敢放开用"两个问题一并解决。
