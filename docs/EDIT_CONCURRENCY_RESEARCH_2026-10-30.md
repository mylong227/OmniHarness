# 并发编辑的三方合并：现役边界研究（2026-10-30）

> 状态：**研究完成 + B1/B2/B3 全部实施**（2026-10-30）。
> 结论：现役 diff3 形状适配本产品；成熟依赖 `node-diff3` 经实测**更差**（同套场景 5 处异常 vs 现役 2 处），
> 按 D10「更优才引」**不引**；唯一真缺陷（行尾静默改写）已用内联归一闪掉，探针 **14/14 正确**。
> 探针：`tools/probes/editMergeProbe.mjs`（`npm run probe:merge`，离线、确定性、恒退出 0）。

## 0. 一句话

本仓的并发编辑合并（行级 diff3 + 字符级细化）在 13 个边界场景里 **11 个正确**，其中
**同点双插入报冲突与 git diff3 同口径**（不是缺陷）、**超大文件如实放弃**、**同改幂等**、**emoji 不被切坏**；
唯一真缺陷是 **CRLF 文件经一次合并会被静默改写成 LF**（整个文件）。

## 1. 现状（已核实，不是推测）

| 事实                                                                            | 位置                                           |
| ------------------------------------------------------------------------------- | ---------------------------------------------- |
| 三方合并 = 行级 LCS diff + 区间聚类 + 单簇字符级细化                            | `src/kernel/util/textThreeWayMerge.ts`                |
| 字符级细化：字符 LCS（按 UTF-16 码元），失败仍冲突                              | `src/kernel/util/textCharacterMerge.ts`               |
| 基线全文（共同祖先）：有界 LRU，单条 ≤512 KiB / 全局 ≤16 MiB / ≤4096 条         | `src/kernel/adapters/tool/fs/sessionBaselineStore.ts` |
| 三条写入工具都用它：`write_file` / `edit` / `apply_patch`                       | `src/kernel/adapters/tool/fs/*.ts`                    |
| **无基线 ⇒ fail-closed**（拒绝并要求重读），不静默覆盖                          | `writeFileTool.writeWithin` 的保守路径         |
| 上限：差分矩阵 2,000,000 单元 ⇒ `too-large`；冲突最多报 8 段；片段最多 600 字符 | `textThreeWayMerge.ts`                         |
| OT（insert-only）与 CRDT（RGA）**只有原语，无生产接线**                         | `textOperationalTransform.ts` / `textCrdt.ts`  |

写入路径的实际分支（读代码得出）：

1. 磁盘现状 == 本次内容 ⇒ 无变化，不写盘；
2. 基线存在且哈希与磁盘一致 ⇒ 直接写（快路径）；
3. 基线存在但磁盘变了 ⇒ **三方合并**：干净 ⇒ 落盘并提示「已自动合并，请复核」；冲突 ⇒ 拒绝并给区间；
   `too-large` ⇒ 拒绝并提示改用 `read_file` 重读 / 拆成 `edit`；
4. 没有可用基线（大文件 / 被淘汰 / 从未读）⇒ **保守拒绝**（陈旧读或并发写都被挡）。

## 2. 方法

探针直接打 `TextThreeWayMerge.merge`（纯函数、无 IO、无模型），13 个最小形态场景，逐条给
「干净合并 / 冲突 / 放弃」+ 正确性判定 + 确定性；并检测**孤立代理项**（字符级 LCS 若按码元切会切坏 emoji）。

诚实边界：这不是真实仓库 diff 的统计分布——它回答「**会不会错**」，不回答「**多常错**」；
也不覆盖两个真实会话同时写盘时的工具层行为（锁、基线读取时序），那属同主题的下半段（§6 的 B3）。

## 3.5 成熟依赖评估：为什么**不**引 `node-diff3`

按 `dependency-allowlist.json` 的 D10（「同等能力下优先成熟依赖」），先实测再决定。候选
`node-diff3@3.2.1`（MIT、无依赖、151 KB）用**数组入参**（自己按 `\n` 切，避开它默认 `/\s+/` 切串），
同一套场景对比：

| 场景                                                 | 现役实现     | node-diff3                     |
| ---------------------------------------------------- | ------------ | ------------------------------ |
| A 不同行 / C 同词不同值 / D 删改 / E 双插入 / K 同改 | ✓            | ✓                              |
| **B 同行不同词**                                     | ✓ 字符级细化 | **✗ 冲突**（它不做字符级细化） |
| **L 紧邻插入**                                       | ✓            | **✗ 冲突**                     |
| **G emoji 邻近编辑**                                 | ✓            | **✗ 冲突**                     |
| **I 磁盘滞后**                                       | ✓            | **✗ 冲突**                     |
| **J 尾随空格**                                       | ✓            | **✗ 冲突**                     |
| **F/F2 行尾**                                        | ✗（B1 后 ✓） | ✓ 冲突（安全但不解决问题）     |

**现役异常 2 / node-diff3 异常 5**（同一 12 场景口径）。结论：它不是"更优的成熟实现"，而是
**更保守的行级实现**——换过去会丢字符级细化、并把四类本可自动合并的编辑变成冲突。
按政策「更优才引」，**不引**；现役实现按政策保留为资产（`@maturity` 已标注）。
若将来只需要「保守 + 与 GNU 语义一致」的 diff3，可重新评估它（触发条件同 §8）。

## 4. 缺陷分析：行尾静默改写（F/F2）

- **机制**：行切分用的是 `split('\n')`，CRLF 行的行尾 `\r` 留在行内容里；当两侧都动了同一片区域时，
  冲突聚类会走**字符级细化**，而字符级 LCS 把 `\r` 当作可丢弃的差异匹配掉 ⇒ 合并结果整片变成 LF。
- **后果**：**内容语义没丢，形状变了**——一个 CRLF 文件在下一次合并写入后整体变成 LF，
  `git diff` 显示全文件改写、`blame` 全红；若仓库有 `.gitattributes` 行尾策略会直接冲突。
- **为什么现在才发现**：这条路径只在「基线存在 + 磁盘被别的会话改过 + 两侧都动了同一区域」时触发；
  单会话、或两侧改不同行时不会走字符级细化（A/I/L 都干净）。探针是第一次把这条路径单独点名。
- **不是缺陷（已确认）**：E 的同点双插入报冲突——`git merge-file` 同样如此，属于正确行为；
  若要「都保留」必须显式约定顺序策略（本仓暂不做，避免语义漂移）。

## 5. 备选方案对比

| 方案                                | 收益                             | 代价                                                                                        | 判断                      |
| ----------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------- |
| **A. 维持现状 + 只在文档承认**      | 零成本                           | 每次合并都可能把 CRLF 改写成 LF（用户可见的大 diff）                                        | 不可接受                  |
| **B. 行尾感知合并（推荐）**         | 修掉唯一真缺陷；改动局限在合并器 | ~40 行 + 判据；要定义"混行尾"的保守边界                                                     | **做**                    |
| C. 字节级合并（把 EOL 当真实差异）  | 不会误改                         | 行尾差异会让**所有**跨风格编辑都变冲突，噪音爆炸                                            | 不做                      |
| D. 接线 CRDT（`textCrdt` 已有 RGA） | 真正无中心实时协同               | 需要文档存储 + op log + 持久化 + 光标；且本产品**没有实时双光标**                           | 现在不做（触发条件见 §8） |
| E. 文件级串行化                     | 消除并发                         | 已有：`WorkspaceFileCoordinator` 写租约；不能替代"事后合并"（回合之间是串行的，跨会话不是） | 已完成                    |

**B 的具体做法（已实施，2026-10-30）**：`TextThreeWayMerge.merge` 入口先判 base 的行尾风格——
base **统一**（全 CRLF 或全 LF）且某一侧也**统一**为另一种风格 ⇒ 先把该侧归一成 base 风格再合并，
结果自然沿用 base 的行尾；base 本身混行尾 ⇒ 一律不动（宁可冲突，也不替用户改写形状）。
实现只有两个私有辅助（`eolOf` / `withEol`），**没有引入依赖**（见 §3.5）。

## 8. 什么时候才需要接 CRDT（触发条件，先写死）

- 产品出现**同一文件的两个实时光标**（协同编辑），或
- 离线编辑后需要**多端收敛**（不是"我改完你改"的回合语义），或
- 实测「合并冲突率」超过可接受阈值（例如每 100 次跨会话写入 > 5 次冲突），或
- 基线淘汰（>512 KiB 文件）导致的「拒绝重读」成为高频摩擦。

在触发前接线 CRDT 只会增加持久化与 GC 的复杂度，换不到任何用户可见收益；`textCrdt` 保持"可证收敛原语"定位。

## 9. 未做 / 边界（诚实）

- 探针只测纯函数合并，**不含**锁竞争、基线读写时序、`.bak` 备份与 `too-large` 后的重读体验；
- 真实仓库 diff 的统计分布未测（「多常错」仍需生产数据）；
- Unicode **grapheme**（组合字符 / ZWJ 序列）未专门覆盖——emoji 场景通过，但不等于所有组合字符都安全；
- CRDT/OT 的接线、GC、光标层**未做**，且按 §8 的触发条件暂不做。
