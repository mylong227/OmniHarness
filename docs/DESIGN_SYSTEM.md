## 1. Design Read（这份 UI 是什么）

| 维度                | 取值                                                                            |
| ------------------- | ------------------------------------------------------------------------------- |
| artifact            | 开发者工作台（对话为主轴 + 遥测/治理侧栏），非营销页、非仪表盘                  |
| audience            | 本机开发者，长时间盯屏、键盘优先、10cm–1m 视距                                  |
| visual-language     | **单色仪器面板**：瑞士式栅格秩序 + 工具型人文（Linear / Vercel / Raycast 一系） |
| mode                | Redesign · Replace（保留全部 class 契约与交互，换掉整个视觉世界）               |
| visual-variance     | 2（极克制：只有明度、字阶、留白三个变量）                                       |
| motion-intensity    | 2（只有 130–190ms 的颜色/透明度位移，无入场大动画）                             |
| information-density | 8（事件流可能上千条，一屏信息量是刚需）                                         |
| asset-dependence    | 1（无品牌素材依赖：自研图标集 + 字符标识）                                      |
| brand-fidelity      | 5（无外部品牌规范，自建并在此固化）                                             |

**定位四问（每个表面都要能回答）**

- **叙事角色**：对话流是主角（hero）；左右栏与顶栏是配角（chrome），必须退到背景里。
- **观看距离**：1m 笔记本 → 正文 13.5px、行高 1.6、侧栏 12–13px；不做投影阅读尺度。
- **视觉温度**：安静、精确、无温度（黑白灰没有冷暖，只有明度）——这是刻意的：界面不表达情绪。
- **容量 check**：单屏（1280×900）须同时容纳左栏 248 + 中栏对话 + 右栏 360；故侧栏信息用 12px
  与紧凑 4px 栅格，中栏正文 13.5px、最大行宽 860px（超过就该换行，不是拉宽）。

**反 AI 陈词（本项目的硬约束，违反即回退）**

1. 不用紫→粉→蓝渐变、不堆 emoji 当图标、不用「圆角卡片 + 彩色左边框」。
2. 不编造数据、不加装饰性分区；每个元素都要能回答"删掉它是否变差"。
3. 图标只用自研线性 SVG 集（`web/src/ui/models/Icon.ts`），不再新增 emoji 图标。
4. **零色相**：任何位置出现饱和色都算缺陷（含状态、徽标、diff、语法高亮、favicon）。

## 2. 色彩：只有一个维度——明度

### 2.1 表面阶梯（surface ladder）

四层表面 + 三档描边。层级靠「明度差 + 发丝线」表达，不靠阴影堆叠。
下表是 `theme.css` 的**出货值**：

| 层                | dark      | light     | 用途                                                 |
| ----------------- | --------- | --------- | ---------------------------------------------------- |
| `--bg`            | `#000000` | `#ffffff` | 中栏对话底、应用底色（暗色=纯黑）                    |
| `--bg-elev`       | `#0a0a0a` | `#fafafa` | 左/右栏底、顶栏、浮层                                |
| `--panel`         | `#161616` | `#f2f2f2` | 卡片、输入区、气泡、面板                             |
| `--panel-2`       | `#252525` | `#e6e6e6` | 卡中卡、下拉触发器、hover 底                         |
| `--code-bg`       | `#050505` | `#f7f7f7` | 机器产物底（代码块、diff、JSON）                     |
| `--hairline`      | `#1f1f1f` | `#e8e8e8` | 栏内分隔线（1.10:1，不承担边界义务）                 |
| `--border-soft`   | `#333333` | `#c9c9c9` | **容器边缘**（1.43:1）：卡片/输入卡/代码块/面板/浮层 |
| `--border`        | `#6e6e6e` | `#767676` | **控件边界**（3.01–4.12:1），承担 WCAG 1.4.11 3:1    |
| `--border-strong` | `#7a7a7a` | `#5a5a5a` | hover / 聚焦的增量提示                               |

> **描边为什么要分三档（2026-10-17 二次校正，来自真实反馈「很多组件边框都粗了」）**
>
> 第一版校正把 `--border` 从 1.33:1 一口气提到 3.55:1，用来补上 WCAG 1.4.11
> 「控件边界 ≥3:1」。但那一刀是**全局**的：连卡片、输入卡、气泡、代码块这类
> **装饰性容器**也吃到了 3:1 的线，满屏都是框，观感立刻变重。
>
> 结论：3:1 的义务只对「**控件边界**」成立（用户要能看出这里可以输入/点击），
> 对「**容器边缘**」不成立——容器的层级由表面明度阶梯表达，不需要靠描边画格子。
> 因此拆成三档，并把使用量按职责分开（实测分布）：
>
> | 档位              | 使用量 | 用在                                                            |
> | ----------------- | ------ | --------------------------------------------------------------- |
> | `--hairline`      | 47 处  | 列表行、栏内区块、粘性表头                                      |
> | `--border-soft`   | 211 处 | 卡片、输入卡、代码块、浮层、面板容器（**默认档**）              |
> | `--border`        | 3 处   | `.form input/select/textarea`、`.tool-status`/`.tr-st` 状态徽标 |
> | `--border-strong` | 31 处  | 一切 hover / 聚焦 / 选中的增量                                  |
>
> 配套：原先散落的 **2px / 3px 装饰性描边**（引用块 3px、错误行 2px、表格合计行 2px、
> 各种 2px 左标）全部收成 1px；只有 **diff 增删行**保留 2px 左缘——那里线本身就是语义
> （`+`/`-` 之外唯一的"这段不一样"信号）。

> **`--hairline` 存在的理由**：全站曾在 200 处引用 `--border`，于是每个容器都被画进格子，
> 界面读起来像线框图（这是「AI 生成感」最直接的来源）。带内分隔（列表行、栏内区块、粘性表头）
> 一律用 `--hairline`，`--border` 只留给真正需要被看见的轮廓。

### 2.2 文本

| token     | dark      | light     | 对比度（on `--bg` / `--panel`）     |
| --------- | --------- | --------- | ----------------------------------- |
| `--text`  | `#ffffff` | `#0a0a0a` | 21.0:1 / 18.1:1（浅色 19.8 / 17.7） |
| `--dim`   | `#a3a3a3` | `#545454` | 8.3:1 / 7.2:1（浅色 7.6 / 6.8）     |
| `--faint` | `#8a8a8a` | `#6b6b6b` | 6.1:1 / 5.2:1（浅色 5.3 / 4.8）     |

`--faint` 用于装饰与**禁用态文字/描边**（单色体系里「禁用」只能靠降对比表达，
不能靠降饱和——本来就没有饱和度）。正文一律 `--text` / `--dim`。

### 2.3 反白强调（「墨水」）

单色体系里「强调」= 与底最大对比的那一档，它同时承担两种角色：

| 角色           | 用法                                              | token      |
| -------------- | ------------------------------------------------- | ---------- |
| 作**底色**     | 主按钮 / 当前会话 / 用户气泡 / 导航当前项 / toast | `--accent` |
| 作**字色**     | 焦点环、选中态文字、链接、进度条、选中区          | `--accent` |
| 落在墨块上的字 | 上述实心块内的文字                                | `--ink-fg` |

dark：`--accent: #ffffff` / `--ink-fg: #0a0a0a`；light 反过来。二者对比度 19.8:1。

> **历史坑（2026-10-17 修）**：旧实现里 `--accent-fg` 才是底色、`--accent` 才是字色，
> 且浅色主题下这对取值与深色相反 ⇒ `refine-surfaces.css` 里「底 = `--accent-fg` /
> 字 = `--accent`」这句注释在浅色下等于「**白底白字**」：用户气泡与页面同色，等于没有气泡。
> 本轮把命名归一（`--accent` / `--ink-fg`），两套主题语义一致。

### 2.4 语义：靠明度 + 字形，不靠色相

| 语义     | token    | dark      | light     | 表达方式（除了明度）                        |
| -------- | -------- | --------- | --------- | ------------------------------------------- |
| 成功     | `--ok`   | `#d4d4d4` | `#3d3d3d` | 中性档 + `✓` 字形；成功是常态，不该抢注意力 |
| 失败     | `--err`  | `#ffffff` | `#000000` | **最亮一档**（反白块）+ `✕` + 实心左缘标    |
| 告警     | `--warn` | `#a3a3a3` | `#545454` | 中间档 + **虚线描边**（唯一的虚线语义）     |
| 新增行   | `--add`  | `#c9c9c9` | `#3d3d3d` | 明度块 + 左缘 2px 实心标 + 行首 `+` 前缀    |
| 删除行   | `--del`  | `#ffffff` | `#000000` | 更亮的明度块 + 左缘 2px 实心标 + 行首 `-`   |
| 中性信息 | `--info` | `#d4d4d4` | `#3d3d3d` | 同成功档（重命名、来源、引用徽标）          |

**铁律**：一屏之内「反白实心块」不超过 2 处（当前项 + 主行动）。单色世界里反白是唯一的
最高音，用滥了就互相抵消——这正是彩色体系「品牌色面积 <5%」的同一条纪律，只是换成明度语言。

> **`color-mix(... , transparent)` 的淡底仍然保留**（如 `--ok` 14%），因为 token 全是灰，
> 混出来仍是灰：它们现在只表达「这一行的明度与邻行不同」，语义完全由字形与前缀承担。

### 2.5 为什么单色（而不是"少用彩色"）

工作台的信息密度极高（事件流 + 遥测 + 治理）。一旦界面上有 8 种色相，颜色就同时冒充
「状态」与「分类」两种语义，信号被稀释成装饰；而**颜色一旦只表示明度**，界面就只剩一条
可读的规则：越亮越靠前。代价是语义必须由字形与形状承担（§2.4），换来的是全站没有一处
颜色需要"记住它是什么意思"。

## 3. 字体

```css
--font-sans: system-ui, 'Segoe UI', -apple-system, 'PingFang SC', 'Microsoft YaHei', …;
--mono / --font-mono: 'JetBrains Mono', 'Cascadia Mono', ui-monospace, …, Consolas, monospace;
```

- **为什么保留系统栈**：本仓铁律是"离线可用、零网络依赖"，不许引 Google Fonts；
  `Inter`/`JetBrains Mono` 只在用户本机已装时命中（`local()` 语义），否则无缝回落。
- **中西文分工**：界面文案走 `--font-sans`；**一切机器产物走 `--mono`**——路径、工具名、ID、
  token 计数、diff、JSON、代码、时间戳、徽标。这条分工是"工具感"的主要来源，比配色更有效。
- **字阶**（`minimal.css §1` 的 `--fs-*`）：11 / 12 / 12.5 / 13 / 13.5（正文）/ 15（面板标题）/
  21（指标数字）。**不做营销页那种 4–6× 比例**：工作台要的是"稳定层级"，不是"海报冲击"。
- **等宽数字**：所有会跳动的数字（计时、token、金额）必须 `font-variant-numeric: tabular-nums`。
- **微标签**：`.col-head` / `.section-title` 等用 10.5px + `letter-spacing: 0.08–0.09em` +
  uppercase——小字号靠字距而非字重取得可读性。

## 4. 间距 · 圆角 · 阴影 · 动效

- **间距**：4px 基准栅格（`--sp-1..7` = 4/6/8/12/16/20/24）。口径是「**组内紧、组间松**」：
  `.ev` 之间 20、过程簇内 2、标题上方 > 下方。
- **圆角**：只允许 **4（微）/ 6（小件）/ 8（控件）/ 12（大表面）/ 999（胶囊）**。
  半径随容器层级递增（控件 6–8 < 卡片 12），层级才读得出来；散落的 5/7/9/10/14/16 已归一。
- **阴影**：**只用于"浮起"**（弹层、抽屉、toast、命令面板），从不用于卡片/输入框/面板。
  `--shadow-1` 轻（菜单）、`--shadow-2` 重（模态）。深色下阴影几乎不可见 ⇒ 深色靠描边 +
  提亮底表达浮起。
- **零装饰**：无渐变（`background-image: none`）、无 `backdrop-filter` 模糊、无内高光、
  无发光焦点环。焦点一律是 2px 反白实环（`outline`），完整覆盖上面各层的 `box-shadow` 环。
- **动效**：`--dur-1: 130ms`（颜色/描边）、`--dur-2: 190ms`（位移/展开）、
  `--ease: cubic-bezier(.22,.61,.36,1)`。**禁止**给 `.ev` 加入场动画（中栏是虚拟列表，
  重挂会重放动画 ⇒ 视觉上一直在闪）。全局尊重 `prefers-reduced-motion`：时长归零，
  但**状态变化仍必须可见**（靠颜色而非位移）。

## 5. 图标 · 代码 · 原生表面

**图标**：唯一来源 `web/src/ui/models/Icon.ts`（自研线性 SVG，24×24 视框、`currentColor`、
圆端圆角）。**铁律：不再新增 emoji 当图标**（字形随系统字体变、尺寸基线不受控、
**不跟随 `currentColor`**，hover/选中态无法与文字一起变色）。
图标恒为装饰性：根节点固定 `aria-hidden="true"`，可读名字由外层按钮的 `aria-label` 提供。
容器里一律要有 `flex: none`（flex 子项默认可收缩，19px 图标会被压成约 8px 宽的竖条）。

**代码高亮（单色化，2026-10-17）**：`highlight.css` 用**字重 + 字形 + 明度**表达层级，
不再用色相（原先是红/紫/蓝/橙/青/绿 8 种）：

| 类别          | 表达                            | dark / light          |
| ------------- | ------------------------------- | --------------------- |
| 关键字 / 函数 | 最亮 + 粗体（骨架）             | `#ffffff` / `#0a0a0a` |
| 字符串        | 次亮 + **斜体**（与标识符区分） | `#d4d4d4` / `#2e2e2e` |
| 数字 / 类型   | 中间调                          | `#bdbdbd` / `#454545` |
| 标点          | 最淡（不该被读到）              | `#a3a3a3` / `#616161` |
| 注释          | 最淡 + 斜体                     | `#8a8a8a` / `#6b6b6b` |

**两条真实缺陷在本轮一并修掉**：

1. **`highlight.ts` 的 class 名与 CSS 不匹配**（`tok-cmt`/`tok-typ`/`tok-pln` vs
   `.tok-com`/`.tok-type`/`.tok-plain`）⇒ 注释、类型、普通文本三类**从来没有拿到颜色**，
   文件预览的高亮一直只对了一半，且不报错、只是"少了一层"，长期没人发现。现已对齐。
2. **vendor 主题在两套主题下都加载**（`vendor/highlight-github-dark.min.css`）⇒ 浅色主题里
   代码块一直是**暗底彩字**。该 `<link>` 已删除；`highlight.css` 移到**最后加载**，
   自己定义单色 token 并覆盖 hljs 的类映射（vendor 文件保持原样不动，回滚成本 = 一行）。

**原生表面**（最便宜、也最容易被跳过的一档）：选区 `::selection` = 反白（与"当前项"同语言）；
插入符 `caret-color`、`accent-color`（复选框/单选）、`scrollbar-color` 与 `::-webkit-scrollbar`
全部跟随 token；滚动条默认几乎隐形、悬停才显形（常驻灰杠在密集界面里最吵）。

### 6.1 按钮语言（全站只有三档）

| 档位       | 外观                       | 用法                                 |
| ---------- | -------------------------- | ------------------------------------ |
| primary    | 反白实心（`--accent`）     | **唯一主行动**（发送、确认、新会话） |
| default    | 发丝轮廓（`--border`）     | 表单行、对话框次要动作               |
| ghost/text | 无框，hover 落 `--panel-2` | 次要动作、图标钮                     |

反白实心在全页**最多 2 处**（当前项 + 主行动）；第 3 处开始互相抵消。

### 6.2 面板可达性（硬契约）

**任何面板都必须有入口，且不得依赖 hash 路由或特定视口宽度。** 收敛前 `RightPanel` 的标签条与
`NavRail` 各写一份清单：变更 / 治理 / 文件 / 详情在标签条里有、在 rail 里没有，而标签条在桌面端
（≥881px）是 `display:none` ⇒ 桌面用户要看「变更」只能手改 hash 或把窗口压窄到 ≤880px。

现在的结构（判据：`web/test/mount.test.ts` 的「面板注册表」用例）：

```
PANELS(16) —— 「全部面板」菜单渲染全集；Router 的 VALID_PANES 与它逐条对齐
```

> **设置为什么不在 PANELS 里**（2026-10-17）：右栏面板都是「看某个东西的状态」，
> 而设置是「改全局配置」——把配置混进监控面板列表，等于让用户在一个为「读」设计的容器里做「写」；
> 而且入口埋在 17 项的选择器里，找一次要点两步。现在设置是**左栏页脚按钮 + 居中模态**
> （`components/SettingsModal.tsx`），与面板注册表彻底解耦，`Router` 也不再放行 `#pane=settings`
> （旧深链安全落回默认面板）。**要加回面板列表前先读那段组件的头注释。**

### 6.3 空 / 加载 / 错误 三态

三者必须**一眼分得开**——原先它们都只是"一行灰字"，用户分不清"这里没数据"和"数据读挂了"：

| 形态          | 何时用                              | 实现                                                           | 观感                                |
| ------------- | ----------------------------------- | -------------------------------------------------------------- | ----------------------------------- |
| `.empty.illu` | 列表为空，**且需要指引下一步**      | `emptyState(icon(...), 主文案, 指引?)`                         | 图标槽 + 主文案 + 灰指引，48px 留白 |
| `.empty.note` | 过程提示（读取中…）/ 结论即全部信息 | `emptyNote(文案, { icon })`                                    | 一行灰字 + 小图标，16px 留白        |
| `.empty.err`  | **加载失败**                        | `emptyNote(文案, { kind: 'err' })` 或 `emptyState(..., 'err')` | 最亮一档 + 2px 实心左缘 + 警示图标  |

错误态用 `emptyState` 时把 `kind` 放在第四参（第三参是指引，可传 `undefined`）。
判据：`format.test.mjs`（结构）+ `a11yContrast.test.mjs`（`.empty.err` 的色必须达 AA）。

## 8. 自检清单（交付前跑）

```bash
npm run web:build && node --test web/test/a11yContrast.test.ts   # 颜色门禁（7 例）
npm run web:test                                                  # 427 例组件契约
node web/test/responsiveProbe.ts --full                          # 真 Chrome 溢出探针
node web/test/visualProbe.ts                                     # 真 Chrome 截图留档（面板 + 交互态）
node web/test/visualProbe.ts --measure                           # 关键元素实测几何
python scripts/checkMonochrome.py web/archive <截图戳>            # 渲染结果的平均彩度（零彩色核验）
```

> **`scripts/checkMonochrome.py` 的口径**：判据是**全图平均彩度 mean(S) < 0.03**，
> 不是「高饱和像素占比」。原因是 Chrome 在 Windows 上用子像素抗锯齿渲染文字，字形左右
> 边缘各有一条橙/蓝描边，单像素饱和度可接近 1.0、整幅占 1–2% —— 拿占比当判据会把任何
> 纯灰界面判成彩色。实测对照：旧世界 dark 截图 mean ≈ **0.199**（成片品牌蓝），
> 单色重设计后 dark ≈ **0.009**、light ≈ 0.009–0.018，相差一个数量级以上。
> 该脚本是**探针**（异常也不阻断提交），用于交付前自证「零彩色」不是一句感觉。

**基线**：截至 2026-10-17 单色重设计，`web:test` **427 例全绿**，`a11yContrast` 7 例全绿，
`scripts/runGates.mjs` 的 fast 层 10/12 条通过，42 张真机截图平均彩度全部 ≤0.0184。

视觉层改动**必须**附上 `web/archive/` 里的真机截图作为证据；只跑单测不算验收——
单测看不见"灰底灰字显得脏"这类问题，而人眼一看就知道。重设计前的对照图存在
`web/archive/baseline-monochrome/`（彩色旧世界），可直接与新图并排比对。

### 9.1 已知残留（诚实边界）

`layout.css` 与 `chat.css` 是**从 HEAD 恢复**的结构层文件（重设计期间脚本改写曾破坏它们，
已整体回滚），因此其中仍留有约 40 处旧世界彩色字面量（如 `.src-badge` 的
`#7fd1ff`/`#ffd27f`、`.change-badge` 的 `rgba(46,160,67,.18)`）。它们**不参与渲染**：
`minimal.css` 在最后加载，已用 token 规则覆盖了这些选择器的 `background` / `color` /
`border-color`（真机截图与平均彩度核验均可证明）。

它们仍是**技术债**：一旦有人删掉 `minimal.css` 的对应规则，彩色就会立刻回归。
清偿方式很直接——在这些选择器上把字面量替换为 `var(--ok)` / `var(--warn)` / `var(--add)`
之类的 token 即可，属于纯机械替换（本轮因脚本两次损坏文件而选择暂缓，避免再冒风险）。
