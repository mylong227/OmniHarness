# 可维护性治理方案（2026-11）

> **性质**：治理方案 + 执行台账（带日期快照）。**唯一目标：把「可维护」变成可测量、可门禁、可预算的东西**，
> 并把当前登记的痛点逐条消除到「不再反复消耗工时」的程度。
> **预算**：10 h/周。**总量**：约 **205 h ≈ 20 周**（分批交付，前 6 周 56 h 先消掉每天都在付的那部分）。
> **不改变** `PROJECT_BOARD.md` 的事实源地位；本文件是「怎么让它继续可维护」的施工图。

---

## 0. 结论先说

**可维护性不是一种品质，是一组可以量化的固定成本。**

每一次改动，你都要付五笔成本：**找（不知道改哪）→ 改（牵一发动全身）→ 验（等不起）→ 发（发不出去）→ 传（教不会别人，包括三个月后的自己）**。
当前这五笔都在涨价，所以「加功能」的净收益在下降——这不是错觉，是可测的：

| 环节 | 当前成本（本机实测）                          | 根因（一句话）                     |
| ---- | --------------------------------------------- | ---------------------------------- |
| 找   | `src` 下 **0/40 模块有 README**；公开面 **242** 个导出 | 没有「读入口」与「契约收缩」        |
| 改   | `adapters` **47,799 行**（占 src 28%）；**4 组**依赖环 | 单模块过大 + 调用点绕道实现文件     |
| 验   | `tsc` 80 s；fast 门禁 193.5 s；**单测 376 s + 前端 283 s ≈ 全量 14 min**（已实测） | 没有分片；CI 从不跑全量                |
| 发   | npm **404**；版本号 **三处不一致**；Release 停在 v0.2.0 | 发布链没有收口                      |
| 传   | `docs/` 根 **47 份 md** + 看板 **7,665 行**；根目录**无** CONTRIBUTING | 文档按「记录」组织，没按「任务」组织 |

**本方案的核心主张**：**先给这五笔成本设预算，再用「删 / 收 / 隔 / 自动 / 契」五种手段把它压到预算内，最后用门禁锁死，防止长回去。**

## 2. 痛点台账（30 项，六域）

消除方式只有五种，写清楚才不会变成"重构冲动"：

- **删**：没有生产调用方 / 重复实现 / 不再维护的分支与文档
- **收**：收敛到一个入口（公开面、脚本、文档、适配器族）
- **隔**：慢的、偶发的、平台相关的移到夜间或可选路径
- **自动**：能让机器判断的，不靠纪律
- **契**：把"约定"变成类型/版本/门禁

## 4. 防复发：把预算钉进门禁

**消掉的痛会长回来**，除非它变成了一个会红的数字。三道闸：

1. **预算门禁**：`maintainability.mjs` 进 `runGates` 的 fast 层（预算超标即红）。
2. **变更纪律**（写进 `CONTRIBUTING`）：
   - 新增依赖必须同时删一个（净零）；
   - 新增公开导出必须同时说明「谁会用」，否则只能 `@internal`；
   - 新增 npm script 必须删一个（净零）；
   - 新增文档必须合并或删除一份（docs 根 ≤12）。
3. **季度审计**（每 3 个月，1 h）：跑一次 §1 的表，把红色项写进下一季度计划——**不允许"观察一季"**。

**净零纪律为什么有效**：它把「加法」的默认成本从 0 变成 1，而人只在默认成本非零时才会认真权衡。

## 5. 稳态维护手册（达标之后，每周 3–4 h）

| 频率 | 事项 | 时长 | 判据 |
| ---- | ---- | ---- | ---- |
| 每周日 | 全量回归 1 次（≤15 min）+ 失败项登记 | 1h | 绿，或红项有归因 |
| 每周 | issue triage（外部 ≥ 每周一次） | 0.5h | 每条有标签/回应 |
| 每月 | 依赖巡检（`npm audit` + 升级 1 个依赖） | 1h | 无 high/critical；无 >12 个月未升级 |
| 每季 | §1 预算审计 + 计划调整 | 1h | 红色项 ≤2 |
| 持续 | 新代码只落在 kernel / contracts / apps 三层内 | — | 落不进去 = 没想清楚 |

**稳态目标：≤4 h/周**（当前 9–18 h/月 只是「维持绿」，还没算救火与尾部风险）。
这个数字是整份方案的**验收指标**：达标 = 可维护；不达标 = 还有没消掉的痛。

## 6. 不可消除项（诚实边界）

以下四条**不会消失**，只能被约束。把它们写进 README，避免未来拿它当失败：

1. **单人维护**：10 h/周 是硬上限。对策不是"更快"，是"更少"——预算 + 净零纪律。
2. **AI 生成代码的可理解性债务**：244 处 TODO 可以清，但「为什么这样写」的语境不可能全部留下。
   对策：模块 README + 契约 + 真实评测，接受"局部不可理解"，用测试兜住行为。
3. **上游依赖变化**（MCP SDK / antd / React / jose）：只能隔离与预算，不能消灭。
   对策：适配器收敛到 3 族、每季度升级一个、断裂时按「删功能」而非「修兼容」处置。
4. **真实评测的成本**：跑真模型要钱要时间。对策：固定 20 个任务、每周一次、结果进看板，不追求规模。

## 7. 与「二开」的关系

本方案是 [FORK_READINESS_2026-11.md](FORK_READINESS_2026-11.md) 的前置条件：
**没有预算与契约，二开就是让别人继承你的维护债。**
两边的映射：A4 ↔ 公开面、A5 ↔ 分层、E1/E2 ↔ 扩展点、D2 ↔ 版本契约、E3/F2 ↔ 贡献入口。
建议顺序：**先做本方案 P0（6 周），再启动二开 P0**——否则你在给别人一个改不动的仓库。
