## 2. 失败模式诊断（`evals/headroom-analysis.mjs`）

33 条查询按「GT 文件在深层候选池中的最佳排位」分类：

- **OK 17 条（51.5%）** — 已命中
- **RANKING 10 条（30.3%）** — GT 在候选池但排不进 Top-10

- **LEXICAL 6 条（18.2%）** — GT 与查询零词法交集（如 "chain of thought persisted to disk" → `StoredTrace`），
  BM25 候选池里**根本不存在**该文件

即：**候选深度 50 已覆盖几乎全部可达空间**，再深无意义。

### 8.1 共同机理（本节最有价值的产出）

1. **网无法同时做到「全覆盖」与「有鉴别力」。** 稠密档（df≤4 ⇒ 482 节点 / 16034 边 / 平均度 **66.5**）
   的 1 跳邻域就吃掉全网 **90.2%**、2 跳 100% ⇒ 处处等价、没有信息量；稀疏档（每节点 top-8）1 跳覆盖
   掉到 90.9% ⇒ 漏网。`evals/spider-density-sweep.mjs` 扫了 4×3×3 组配置，**不存在甜点**。
2. **网的拓扑类型错了。** 文件级网连的是「**结构性**关联」（两文件共享罕见标识符），而词法盲区要的是
   「**语义**关联」——`StoredTrace` ← "chain of thought **persisted** to disk"、`Canonicalizer` ←
   "what **normalizes** text"。**结构边在语义鸿沟上够不到，这不是调参能解决的。**
3. **零依赖的分布统计吃不到语义红利。** 词级共现网选出的扩展词是「共现显著但**不同义**」的长尾词
   （`semweight` / `turnoutcome` / `modulus`），与 LSA 证伪（精确率腰斩）、PRF 仅 +3pp 同源。
4. 这是**第 4 次独立确认「扩大可达集」对本语料无效**（前有 `pool-depth-probe.mjs`、
   `rank-veto-retro.mjs`，以及本节的 ①②③）。

## 9. 军事链条五级：「排序层」不可再增，「弹药层」砍 69.9% token 且反手提命中 +6.1pp（2026-09-17 追加）

按「雷达探测 → 太空卫星定位 → 高精度导弹 → 暴雨梨花针 → 高射速近防炮」的五级构想逐级翻译为算法原语
并实测。**结论：排序层的命中率增益全部不显著（诚实判负）；真正落地的是「弹药投送」——它把注入 token 砍
69.9%，而省下的预算反手把命中率推高 +6.1pp。**

### 9.1 先对标业界（我们差多少）

| 系统                                         | SWE-bench Lite 文件级定位 Acc@1 / Acc@5 |
| -------------------------------------------- | --------------------------------------- |
| 纯 BM25（单路词法）                          | 38.7% / 61.7%                           |
| 代码嵌入检索（CodeRankEmbed）                | 52.6% / 84.7%                           |
| agent 类（LocAgent / OpenHands / Agentless） | 72–78% / 79–94%                         |

另据 Sourcegraph：**BM25F（多字段 BM25，奖励符号定义与文件名命中）在其内部评测中关键指标约 +20%**，
两段式架构为「BM25 召回 → transformer 精排」。我方对抗口径 hitRate@14 **69.7%** / @20 **75.8%**
（n=33、语料 482 文件），与「嵌入检索」同量级，而**零依赖、零模型**。

### 9.2 五级翻译与裁定（配对 bootstrap，n=33）

| 军事级                   | 算法原语                                                      | 裁定                                                               |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------ |
| ① 雷达探测（多频段）     | 多字段 BM25F：content / path / symbols / signature 独立归一化 | 命中率**不显著**（K=10 +6.06pp [−6.06, 18.18] 跨 0）；token↓、MRR↑ |
| ② 太空卫星（全域标定）   | 跨频段分数校准（max-norm / 排名分位）                         | MRR 0.318 vs 基线 0.258；命中率仍不显著                            |
| ③ 高精度导弹（精确制导） | 字段感知精排（倒数秩 + 符号名覆盖 + 路径覆盖）                | **对强池有害**（66.7% &lt; 不重排 69.7%）；对弱池 +9.1pp（历史）   |
| ④ 暴雨梨花针（一发多针） | RRF 多探针融合                                                | 命中率 **+0pp**；MRR **+10.14pp**（CI 跨 0）                       |
| ⑤ 高射速近防炮（末端）   | 自适应预算 / 末端补射                                         | 未形成独立增益；真正形态是**梯度弹药投送**（§9.3）                 |

一处反直觉发现：**`signature` 是被完全浪费的强信号** —— 单频段命中率即 **69.7% @14 追平生产默认**，
且 token 少 34%（2197 vs 3335）。它与 `symbols` 同属「声明信息」，而 `content` 是「实现信息」。

### 9.3 真正的收益：把「命中哪些文件」与「注入多少字」解耦

**核心洞察：命中哪些文件由**排序**决定，注入多少字由**呈现**决定。** 由此设计梯度投送
（`src/context/repoMap/repoMapPayload.ts`）：

- 前 3 个文件 → 完整符号大纲；
- 第 4..8 个 → 「`📄 路径` + 命中符号名」；
- 其余 → 仅一行 `📄 路径`（agent 有 read 工具，路径本身即线索）。

| 口径（生产 symK=24，33 条查询） | 全大纲 | 梯度投送 | 降幅   |
| ------------------------------- | ------ | -------- | ------ |
| fileK=20 平均 token             | 4829   | **1455** | −69.9% |
| 应急压缩档（`degrade`）         | 4829   | **911**  | −81.1% |

**构造性不变量（非统计推断）**：排序结果 `query().files` **33/33 逐字相同** ⇒ `hitRate@K` **必然不变**，
不存在「为省 token 而掉召回」的风险。**省下的预算反向兑换覆盖广度**：fileK 14 → **20** ⇒
命中率 **69.7% → 75.8%（+6.1pp，CI [60.6, 87.9]）**，而 token 仍**低于**原 14 档全大纲口径（3703）。

**P5 降档改口径**：原降档靠「缩 fileK 10→5」（代价 −12.1pp 命中率）却几乎不省 token——梯度投送下
fileK 5→10 只差 **34 token**，因为 token 大头是**前几档的完整大纲**，尾部路径行每行约 7 token。
改为**收缩大纲档位**（只留 Top-1 完整大纲）后：K=14 档 **946 token**（比旧降档 1337 少 29%）且
命中率 **69.7%**（旧降档 36.4%，**+33.3pp**）。

### 9.4 诚实边界

1. **排序层零改动落地**——多字段 BM25F 与 RRF 的命中率增益在 n=33 下均不显著，按「两关」纪律不翻默认，
   只留评测脚本与报告。**这一批的贡献是「成本」，不是「命中率」。**
2. 梯度投送降低的是**注入字面信息量**；`hitRate@K` 构造性不变，但**下游任务完成率是否同步不变未验证**，
   须待 P6 端到端基准——本报告不对此作承诺。
3. 一处**信息反而增加**：`outlineText` 只列**有声明符号**的文件，梯度档对每个命中文件都给路径行 ⇒
   命中集含无符号文件时梯度档**更全**（33 条中 2 条属此情形）。
4. 自然口径命中率已达 **100% [100, 100]**（fileK=20 档）。
5. **评测脚本自身缺陷已修并留档**：`military-verdict` 初版把「多字段全量排序」与「基线 K 截断」相比，
   得出虚假的 **+39.39pp**；修正为同 K 截断后回落至 **+6.06pp [−6.06, 18.18]**（不显著）。
   教训：**比较前必须确认两侧预算口径一致。**

## 10. E2E 出分通道：hitRate 之外的那一关（2026-09-17 追加）

**动机**：本调研所有结论都是 `hitRate@K`（文件集合口径），**不等于端到端任务成功率**。要回答
「提命中会不会真的让 agent 解得更对」，必须有一条能真跑的**判分通道**。本轮把它打通到「gold 可判
resolved」的程度。

### 10.1 国内通道（用户指令「采用国内同等的题解决」）

- **Gitee `mirrors/` 组织**：12 个 SWE-bench 仓库中 **11 个可达**，`base_commit` 抽样 **22/22 命中**
  （Gitee OpenAPI 校验）；仅 `pylint-dev/pylint` 无镜像。映射见 `benchmark/swebench-gitee-mirrors.json`。
- `NativeExecutor` 增 `repoMirrors`（上游 slug → 镜像 slug，缓存目录仍按上游命名 ⇒ 换源不失效），
  CLI 增 `--repo-base` / `--repo-mirrors` / `--env-pins`。

### 10.2 「两关」暴露的环境保真度缺口（本轮最重要的工程发现）

E2E 冒烟必须走**两关**（沿用仓库 D6「放行 ≠ 有效」）：

| 关     | 判据                                         | 意义                                    |
| ------ | -------------------------------------------- | --------------------------------------- |
| 第一关 | 空补丁 ⇒ `resolved:false` **且 reason 为空** | 通道通（跑完 clone→venv→pytest 全流程） |
| 第二关 | **官方 gold patch ⇒ 必须 `resolved:true`**   | **判定器有效**（不是恒假）、环境够保真  |

**只做第一关会得到「通道已通、可以出分」的错误结论**。实跑：第一关 ✅ 通过（24.1s），
**第二关 ❌ 未通过** ⇒ 逐段打印 pytest 产物定位两个真因：

1. **registry-latest pytest 顶掉仓库 pin**：旧实现无条件 `uv pip install pytest pytest-timeout`
   ⇒ pytest **9.1.1**，而 pytest 9 移除了 `monkeypatch.notset` ⇒ flask 老套件 **60/60 ERROR**
   （仓库自述 `requirements/tests.txt` 实为 `pytest==7.2.2`）。
2. **不设上界的开发期运行时依赖被解析到过新主版本**：flask 2.3.0.dev 声明 `Werkzeug>=2.2.2`（无上界）
   ⇒ **werkzeug 3.1.8**（删除了 `werkzeug.__version__`）⇒ 套件崩。

**修法**（`src/eval/pythonEnvPlan.ts`，纯规划器、可单测）——安装阶梯：
①仓库本体 `-e .` → ②可选 extras → ③**仓库自述的已 pinned 测试依赖文件**（7 档候选）→
④**该仓库额外约束**（`envPins` + `benchmark/swebench-env-pins.json`）→ ⑤**仅在 pytest 缺失时**兜底安装
（**绝不覆盖仓库 pin**）。本质是**用「仓库自述 + 显式约束」逼近官方 harness 的预建 conda 镜像**。
**修后第二关通过**（`pallets__flask-5014` gold ⇒ `resolved:true`）。

### 10.3 FAIL_TO_PASS 解析 fail-open 缺陷（安全级）

官方数据集把 `FAIL_TO_PASS`/`PASS_TO_PASS` 存成 **JSON 字符串**，而 `loadVerified` 仅做类型断言
`as readonly string[]`（运行期不解析）⇒ ① 直接 `failToPass.every` 抛错；② 更危险：**若被上游 catch 成
`[]`，`[].every()` 恒真 ⇒ 任何补丁都被判 resolved（假绿）**。已修：`parseTestList` 统一收口 +
**空 `FAIL_TO_PASS` 拒绝加载**（`PASS_TO_PASS` 允许空，官方 **11/500** 合规）+ 执行边界纵深防线。

### 10.6 ★真实出分：梯度投送「省 token 不伤解题率」（2026-09-17 追加）

**问题**（用户原话）：梯度投送省 token 是否会**拖慢 agent 端到端解题成功率**？此前只有 `hitRate`，
**不等于任务成功率**。现在用真实模型 key（`deepseek-chat`，temp=0）在**同一批 16 题**上跑两档投送形态，
**除投送形态外逐字相同**（检索复刻与生产入口逐字节自证，见 `benchmark/swebench_predict.mjs`）。

| 形态       | resolved         | 平均地图字符 | 平均 prompt token          | 平均修复轮 |
| ---------- | ---------------- | ------------ | -------------------------- | ---------- |
| **tiered** | **7/16 (43.8%)** | **12,410**   | **62,667**                 | 1.93       |
| **full**   | **7/16 (43.8%)** | 58,554       | 88,731                     | 2.00       |

- **配对**：5 题两形态皆 resolved、7 题皆未过、各 2 题单侧成功 ⇒ McNemar b=2/c=2（无差异证据）。

## 11. LSP 候选源**真机实测**（2026-10-02 首次跑通，但收益未证）

此前 `evals/probe-lsp-candidates.mjs` 在任何 Windows 环境上都恒定 `SKIP`，故该路**从未被真机验证过**。
本轮排查修掉两处真实缺陷后首次跑通：

| #   | 缺陷                      | 根因                                                                                                   | 修法                                                                                     |
| --- | ------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 1   | 探针恒 SKIP               | `serverReachable()` 用 `command -v`——这是 **POSIX shell 内建**，Windows 的 cmd.exe 里根本不存在 ⇒ 永假 | 改为直接 `spawnSync(cmd, ['--version'])` 判 ENOENT（跨平台）                             |
| 2   | 适配器 `spawn npx ENOENT` | Windows 上 PATH 里的入口绝大多数是 **`.cmd` 包装**，Node `spawn` 不带 shell 时不解析它们               | `lspJsonRpcConnection` 仅在 `win32` 借道 cmd.exe（Linux/macOS 仍 `shell:false`，零回归） |

**实测结果**（`typescript-language-server 6.0.1`，902 文件语料，5 条锚点查询）：

- **5/5 成功、0 失败、5/5 产出候选**，单查询延迟 **26–89ms**（远快于预期，不是吞吐瓶颈）；
- 但**候选量很小**：每查询只扩展出 **1–3 个文件**、0–9 个符号。

⇒ **结论要分开说**：**通路可用**（此前只是没人验证过），但**「能扩展出候选」不等于「提升召回」**——
在 fileK=20 的预算里只补 1–3 个文件，边际贡献可能很有限。要宣称收益必须再走第 2 关 AB
（同 corpus、开关隔离 + bootstrap CI），**本轮未做，不得写进任何对外口径**。

列表尾部**（`repoMapContextEngine.ts:456-457`），经 RRF（k=60）加权后排在很后面，却把**与 BM25 重合**的
文件在同一条列表里计了两次分（`semanticIndex.ts:148` 按出现次数累加）⇒ 少数被 LSP 重复命中的文件
反而挤掉了原本排在前面的 GT 文件，这解释了「提升 22 / 下降 23」几乎对称、而点估计为负的现象。

**这是第 6 次独立确认「扩大候选源 / 改变候选源对本语料无效」**（前 5 次见 §3 与「蜘蛛网五形态」节），
且这次是**唯一一次针对「真实语言服务器」的**——它把该路线从「未验证」推进到「已验证为负」，

（无语言服务器时干净 SKIP，并落 `status:'SKIP'`，**不伪装成「增益为零」**）。
