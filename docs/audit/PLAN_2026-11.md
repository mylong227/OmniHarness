# 盘点与方案：把 `audit` 从「自证可用」推到「陌生人可验证」（2026-11-03）

> **性质**：决策 + 施工方案（带日期快照）。不改 `PROJECT_BOARD.md` 的进度状态——看板仍是唯一进度事实源。
> **口径**：`事实`（本机可复核，附命令）/ `推断`（我的判断）/ `预测`（可被时间证伪）。
> **上游**：[`STRATEGY_2026-11-02.md`](../STRATEGY_2026-11-02.md) §6（R4 收缩 + 单点外化）、看板 §207（audit 落地）。
> **本机约束**：<10 h/周，全开源，可离线私有化，不做销售。
> **排版约定**：本文里**尚未存在的规划文件**一律写成 plain text（不加反引号）——
> `docLinkCheck` 会把反引号里的仓库路径当「提及」并判死链，而规划文件在落地前必然不存在。
> 这是本仓门禁的真实口径，不是排版洁癖（见 §1.4 ①）。

## 0. 一页结论

1. **全仓唯一「闭环」的应用是 audit**：23 个文件 / 4,193 行，**零运行时依赖**（只 import `node:*` 与相对路径），
   输入 → 报告 → 第三方独立复核 → 退出码，四步闭合。其余应用（cli / server / web）都是「平台面」，
   规模大 3–9 倍，但产物是「人看着用」，没有可交给第三方的凭证。
2. **audit 现在缺的不是功能，是「对外可验证性」**：npm 未发布、包 14.2 MB、要求 Node ≥22.14、
   报告无脱敏、无签名、真实厂商格式未在真实文件上复核过。这五条里，**前三条决定「有没有人试」，
   第四条决定「敢不敢发给别人」**。
3. **方向不变（R4），重心从「造」移到「证 + 分发」**。度量从「功能数」换成「外部可复现证据数」
   ——具体就是：陌生人能不能在 5 分钟内、不登录、不配 key、看到一张自己能复核的报告。
4. **90 天预算 ≈104 h（含每周回归）**，七个工作包 P0–P6，每包都有可执行验收命令。
   **D90 = 2027-01-31**，按 STRATEGY §6.6 判决：继续 R4 / 减半续期 / 转 R5。

### 1.2 六条判据（推断，非客观分数）

| 判据                  | 含义                                                 | audit | cli  | server | web  |
| --------------------- | ---------------------------------------------------- | :---: | :--: | :----: | :--: |
| C1 闭环               | 输入→输出→**第三方**可复核，不需要作者在场           |  ✅   |  ❌  |   ❌   |  ❌  |
| C2 边界诚实           | 认不出就失败，不猜、不产空报告                       |  ✅   | 部分 |  部分  | 部分 |
| C3 判据密度           | ≈10.5 例/千行（44 例 / 4.2k 行），且含**篡改正对照** |  ✅   |  中  |   中   |  中  |
| C4 依赖面             | 零运行时依赖、不接模型、不联网、不要 API key         |  ✅   |  ❌  |   ❌   |  ❌  |
| C5 可分发             | 单命令、离线、体积可接受                             |  ⚠️   |  ❌  |   ❌   |  ❌  |
| C6 维护面（改动半径） | 只读文件，维护面 = 解析 + 渲染                       |  ✅   |  大  |   大   | 最大 |

**裁决：audit 9.4 / 10。** 扣的 0.6 全在 C5 与「对外可用性」：今天它只有作者能跑通
（需要 `npm run build` + 本地 dist + 会读源码），还没到「npx 一条命令」的形态。

### 1.3 它凭什么算「完美」——四条结构性的、可复核的

1. **双层完整性，且第二层可被判据钉死**：载荷哈希链
   `hash_n = SHA-256(prev_n + "\n" + canonical(record_n))` **加上** 文件级自指纹
   （把 `artifact.sha256` 换成占位后整份文本的 SHA-256）。于是「只改页面一个显示字符、不动内嵌 JSON」
   也会被 audit verify 判 `artifact`——这是出证工具与「好看的报表」的分界线。
2. **诚实边界写进了代码注释与文档**（`auditChain.ts` 明说「这是完整性检测，不是签名」；
   README 写「不识别即失败」）。全仓把它当文化，但只有 audit 把它做成了**行为**（exit 2）。
3. **篡改正对照是实测过的**（看板 §207.4：改 `<h2>` ⇒ `artifact` 红；改载荷内文 ⇒ `hash` 红并给下标），
   不是「我觉得应该能检出」。
4. **零运行时依赖**：`src/apps/audit/*.ts` 的外部 import 为空——因此它天然可离线、可私有化、
   可被单独打包（P1 的技术前提）。

### 1.4 它离「完美」还差什么（三条真实裂缝，含证据）

| #   | 裂缝                         | 证据                                                                                                                                                        | 影响                                              |
| --- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| ①   | **死链：信任模型文档不存在** | `src/apps/audit/auditChain.ts:9` 指向 docs/AUDIT_ATTESTATION.md（**不存在**）；`scripts/docLinkCheck.mjs:14` 只扫 `*.md`，**扫不到 `.ts` 注释**             | 出证工具最关键的一段说明（完整性≠来源）无正式文档 |
| ②   | **不能对外发**               | 报告含完整 prompt / 命令 / 输出 / 绝对路径，当前无任何遮蔽旋钮（看板 §207.6 自认）                                                                          | 「发给内审/法务/客户」这一步走不通                |
| ③   | **不是一条命令**             | npm 未发布（`npm whoami` = `ENEEDAUTH`）；`files` 打包 14.2 MB（`dist/src` 3.0 MB + `web/dist` 11.2 MB）；`engines.node >= 22.14`；`bin` 指向全量 `exec.js` | 陌生人「5 分钟见效」不成立，demo 只能作者演示     |

> ①是「完美应用」上的发丝裂缝，但它恰好长在**最该严谨的那句话**旁边——所以列进 P0，不列进「以后清理」。

> **不再证明「能造」，开始证明「别人能用、能复核、敢转发」。**

三段式（与 STRATEGY §6.4 对齐，但按 11-03 的真实进度重排——MVP 已提前落地）：

| 阶段   | 区间                     | 唯一目标                         | 验收信号                        |

| 任务 | 做什么                                                                                                                                         |

| T4.1 | `--sign <ed25519-key>`：签名覆盖 `head + artifact.sha256 + redaction 摘要`；audit verify `--public-key <pem>` 校验；`--require-signature` 强制 |
| T4.2 | 文档：信任三列（完整性 / 来源 / 时间），明确「无签名 = 只防改，不防伪」；密钥分发与信任根不在本工具职责内                                      |
