# 信任模型：审计报告能证明什么、不能证明什么

> **一句话**：哈希链与文件级自指纹证明「报告自生成后未被改动」；它们**不证明**
> 「会话本身真实」与「报告出自谁之手」，时间也要靠外部锚点。`src/apps/audit/auditChain.ts`
> 顶部注释与 `auditTypes.ts` 的设计口径都指向本文——这里是唯一的正式表述。
>
> 上游：[README.md](README.md)（用法与算法）、[EXIT_CODES.md](EXIT_CODES.md)（退出码契约）。

---

## 1. 三列信任表

| 维度       | 能证明什么                                                                                                                           | 不能证明什么                                                                                            | 补强手段                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **完整性** | 报告（载荷 + 展示层）自生成后**逐字节未被改动**：改一条记录、删一条记录、换顺序 ⇒ `hash`/`prev` 红；只改页面显示字符 ⇒ `artifact` 红 | 输入会话文件本身的真实性（`source.sha256` 只把报告与**那份文件**绑定，不判断那份文件是不是伪造/拼接的） | 报告与输入文件一起交存第三方；输入文件的哈希单独留档                                           |
| **来源**   | （什么都不证明——这是刻意的）链是任何人都能重算的公开算法，报告内不含任何秘密                                                         | 「报告是谁生成的」「在哪台机器生成」——任何拿到报告的人都能重算一条自洽的新链                            | 外部签名（Ed25519，规划中）；或由调用方在自己的留存系统里登记报告哈希                          |
| **时间**   | `generatedAt` / 记录时间戳在链内**未被改动**（改了时间链就断）                                                                       | 时间戳本身的真伪——生成器可以写任何时间，时钟可以错                                                      | 外部时间戳（RFC 3161 TSA）或「生成后立即发布到带时间的第三方渠道」（邮件、git push、工单系统） |

**记忆口诀**：链防「改」，不防「伪」，不证「时」。

## 2. 复核失败原因的完整清单

`audit verify` 的失败原因（`reason`）与含义——复核方可以按此表核对自己的第三方实现：

| reason             | 含义                                             | 检出对象                                             |
| ------------------ | ------------------------------------------------ | ---------------------------------------------------- |
| `schema`           | 载荷不是 `omniharness.audit.report/v1`           | 载荷整体被替换                                       |
| `algorithm`        | `integrity.algorithm` 不是 `sha256`              | 完整性头被改                                         |
| `genesis`          | 创世哈希不是 64 个 `0`                           | 链起点被改                                           |
| `prev` / `hash`    | 第 N 条记录的前驱/本条哈希重算对不上（给出下标） | 记录内文被改 / 记录被换                              |
| `count`            | `integrity.count` ≠ 实际记录数                   | 「有多少条」被改                                     |
| `head`             | 链头对不上                                       | 末条记录或链头被改                                   |
| `summary`          | `summary.total` ≠ 实际记录数                     | 「摘要里的记录数」被改（JSON 形态的主要防线，见 §3） |
| `coverage`         | `coverage.recognized` ≠ 实际记录数               | 「载入时间线的记录数」被改（同上）                   |
| `artifact`         | 文件级自指纹对不上（HTML / Markdown）            | **展示层**被改（只改页面文字不动 JSON）              |
| `artifact-missing` | 自指纹字段缺失或形状非法（HTML / Markdown）      | 「删字段 + 改展示」的绕过尝试                        |

## 3. 覆盖率口径（`coverage`）

报告头新增 `coverage: { recognized, unrecognized }`，回答复核方的第一个问题：
**「这份报告覆盖了源文件的全部内容吗？」**

- `recognized` = 载入时间线的记录数（= `records.length` = `summary.total` = `integrity.count`）。
  四个数字必须相等，`verify` 对后两个做机械对账（`summary` / `coverage` 两种失败原因）。
- `unrecognized` = 解析器**明确不认识**的来源条目数（条目 = JSONL 一行 / 信封里一条事件）：
  1. 坏行（不是合法 JSON）；
  2. 解析出来不是对象（数组、标量）；
  3. 顶层类型缺失，或该格式的解析器不认识这个类型；
  4. ACP：不是 JSON-RPC 帧、method 认不出、`session/update` 的 update 类别认不出。
- 未知**顶层类型**的条目同时以 `other` 类记录**原样保留**在时间线里（证据不丢），
  所以它既计入 `unrecognized` 也出现在 `records` 中；未知**消息内容块**（一行消息内部的
  局部块）不单独计数——它们已作为 `other` 记录可见，两个口径的差值由此解释。

**诚实边界**：`recognized` 可由 verify 独立重算；`unrecognized` 没有独立重算来源
（复核方拿不到源文件），在 HTML / Markdown 里由文件级自指纹保护，在 JSON 里与
`title` / `tokens` / `source` 一样属于「链内数字但无第二来源」——这是 JSON 形态的固有边界，
不是遗漏。要对 `unrecognized` 追责，请对 HTML 形态复核或同时交付源文件。

## 4. 为什么刻意不加 HMAC / 签名（现状）

出证报告是**交给对方看**的：密钥不能随报告交付（否则对方改完重算即可），HMAC 模式
（`src/kernel/util/hashChain.ts`，服务于落盘日志防篡改）在「第三方复核」场景下反而让对方
无法验证。两者场景不同，不合并。来源证明（签名）与外部时间戳的接入方式见
[README.md](README.md) §6「还没做」——按 90 天方案（`docs/audit/PLAN_2026-11.md` P4）
在外部信号出现后再上。
